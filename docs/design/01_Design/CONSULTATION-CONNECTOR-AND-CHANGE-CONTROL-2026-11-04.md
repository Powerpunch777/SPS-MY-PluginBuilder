# 상담 Connector·명시적 분석·설계 변경관리 개정

- 결정일: 2026-11-04 (KST)
- 상태: 사용자 확정 설계. 구현·연동·테스트 완료 보고가 아니다.
- 적용 기준: v15, CSAS 누적 설계 v0.8의 D3·Revision·G5 및 5개 Lead 논리 세션.
- 우선순위: 상담 수집을 수동 일회성 Batch로만 제한하던 v15 §2C 및 이에
  의존한 인수 기준의 상충 문구보다 이 결정이 우선한다. 상충하지 않는
  원문 보존·출처·Workspace 격리·권한·사용자 승인 경계는 유지한다.

## 1. 상담 수집과 분석 분리

크몽 등 외부 플랫폼의 상담 메시지는 Connector를 통해 실시간 동기화한다.
메시지 수신 경로는 원본 저장, 중복 제거, 순서 관리만 수행한다. 상담 원본은
지속적으로 보존한다. 메시지가 들어올 때마다 Lead를 자동 실행하거나 상담을
분석하거나 요구사항·설계를 자동 수정하지 않는다.

실시간 Connector는 수집 방식이고 AI 직원이나 별도 상담 분석 세션이 아니다.
실시간 수집 허용은 자동 AI 분석·설계 개정·CTO 배정·Worker 실행 승인이 아니다.
Connector 연결 상태와 분석 상태는 독립적으로 표시한다.

이 결정은 특정 플랫폼의 공식 API·Webhook·Export 제공 사실을 증명하지 않는다.
플랫폼별 실제 허용된 취득 경로와 인증·권한·수신 방식은 조사·검증 후 명시한다.
미연결·지원 불명은 그대로 표시하고, 임의로 실시간 동기화 성공을 연출하지 않는다.
로그인 우회, 비인가 스크래핑, CAPTCHA 우회, 세션 쿠키·토큰 추출은 허용하지 않는다.
외부 연결·실제 고객 데이터·새 권한의 운영 적용은 별도 확인한다.

원본 메시지 식별자·출처·수신 순서와 원본이 제공하는 순서·시각을 구분해
보존한다. 중복 제거가 원본의 조용한 덮어쓰기·삭제를 뜻하지 않는다.
실제 누락·충돌·순서 불확실성을 완전 수집으로 표시하지 않는다. 상세 저장
계약은 기존 Core/SDK 원시기능 위에서 Builder가 소유한다.

수동 TXT/CSV/JSON 입력 형식에 대한 이전 질문은 이 결정으로 재범위화됐다.
사용자가 특정 CSV/JSON 양식이나 일반 TXT 메시지 경계 규칙까지 승인한 것은
아니다. 기존 수동 가져오기 구현은 보존·재사용 가능성을 검토하되 실시간
Connector 또는 전체 새 흐름의 완료 증거로 대체하지 않는다.

## 2. 최초 설계 확정 전

1. Connector는 상담 원본을 누적한다. 분석은 자동으로 시작하지 않는다.
2. 사용자가 명시적으로 `상담 분석 시작`을 실행한다.
3. Lead Main은 그 시점까지 누적된 상담을 분석해 요구사항과 초기 설계문서를 작성한다.
4. 사용자와 Main이 설계를 협의하고, UI Design에서 UI를 설계·검토한다.
5. 사용자 승인에 따라 Main의 공식 발행 경로로 Design Baseline을 확정한다.

분석 실행에는 대상 Workspace, 원본 ID·출처, 해당 시점 분석 범위가 연결되어야
한다. 실행 중 새로 도착한 메시지가 분석 대상이나 승인 설계를 몰래 바꾸지
않아야 한다. 상세 cursor/watermark·동일 요청 재시도 계약은 기술 설계로 고정하고
기존 기록·실행 기능을 재사용한다. 범위가 불명확하면 성공으로 간주하지 않는다.

최초 Design Baseline 이전의 대화·요구사항 정리는 초기 설계 작업이다.
Baseline 이후의 변경관리와 혼동해 미승인 초안을 CTO 구현 지시로 발행하지 않는다.

## 3. Baseline 이후 변경관리

추가 상담은 계속 수집하되 기존 승인 설계를 직접 덮어쓰지 않는다. Lead가
원본과 기존 기준선을 대조해 다음 종류를 구분한다. 사용자의 의도·업무 의미
판단은 Lead의 책임이며 단어·문구 하드코딩으로 분류하지 않는다.

| 종류 | 의미 | 경계 |
| --- | --- | --- |
| Clarification | 설명 보충 | 구현 범위 변경을 숨겨 통과시키지 않는다. |
| Correction | 오류 정정 | 원본·이전 기준선·정정 근거를 보존한다. |
| Change Request | 범위·기능 변경 | 영향 분석과 사용자 승인 전 구현하지 않는다. |

Change Request는 기존 설계와 비교해 요구사항, UI, 기술, CTO Workstream,
Task, 일정, 상품 범위에 미치는 영향을 분석한다. 사용자 승인 후 새로운
Design Revision을 생성한다. 영향받지 않는 설계와 작업은 유지한다.
원래 승인·판단·검증 이력을 삭제하거나 전체 작업을 일괄 무효화하지 않는다.

분류 결과·출처·승인·영향 분석이 실행 권한과 연결되어야 한다. CTO나 Worker는
승인되지 않은 변경을 임의 구현할 수 없다. 관련 작업만 보류하고 승인된
독립 작업은 계속한다. 설명 보충·오류 정정이라는 이름만으로 변경 Gate를
우회하지 않는다. 각 종류별 상세 발행 조건이 새 정책 선택을 요구하면 사용자에게
질문하고 답변을 이 설계 또는 후속 확정 개정에 반영한다.

## 4. CSAS D3·Revision·G5 연결

| 기존 영역 | 통합 계약 |
| --- | --- |
| D3 지속형 질문 탐지 | 원문을 누적할 수 있으나 수신 이벤트마다 분석 Run을 자동 시작하지 않는다. 명시적 상담 분석·사용자/Lead 협의·개발 중 질문 처리에서 누락·모호함·모순을 조사한다. |
| Revision | 수집 원본과 분석 대상·초안·승인 Baseline·변경 제안·승인된 새 Revision의 ID/출처를 분리하고 기존 버전을 보존한다. |
| G5 | Baseline 이후 CR의 old/new 요구·UI·기술·Graph·CTO·Task·일정·상품 범위 영향과 승인 근거를 연결한다. 관계 불명은 UNKNOWN/REVIEW이며 무영향 증명이 아니다. |
| G3/G4 | 승인 Revision 및 영향 처리 상태를 Workstream/Task 발행·실행 시 확인한다. 수집·분류만으로 구현을 허가하지 않는다. |
| UI 변경 영향 | 승인 HTML·UI Contract·UI Revision 및 양방향 관계를 재사용하고 영향받는 부분만 재검토한다. |

## 5. Lead 5세션 연결

- **Main:** 사용자 명시 분석을 시작하고 요구사항·설계·분류·영향 분석을 통합한다.
  사용자 결정을 받아 공식 Baseline/Revision을 발행한다.
- **UI Design:** Main의 승인 기준과 연결해 UI를 설계하고 변경 영향을 제안한다.
  외부 상담 수신만으로 UI 승인을 바꾸지 않는다.
- **Background:** 허용된 계획·조사·영향 분석을 지원한다. Connector 수신이
  상주 분석이나 자동 실행을 켜는 신호는 아니다. 공식 발행은 Main 경로를 따른다.
- **Question Intake:** CTO가 작업 중 발견한 질문을 Lead로 올리는 내부 경로다.
  외부 상담 Connector의 입력함으로 바꾸지 않는다.
- **Question Discussion:** Lead가 사용자 결정이 필요한 질문만 사용자와 협의한다.
  답변은 원문 근거와 공식 설계 개정으로 연결한다.

5세션은 프로젝트 기억·승인 설계·결정을 원본 ID와 출처로 공유하되 대화 전체를
복제하지 않는다. 최신 승인 Revision·결정 조회와 Main 발행 경계를 유지한다.
세션 이동은 AI 실행이나 상담 분석 시작 명령이 아니다.

## 6. 개정 인수 기준

다음은 기존 162개 정의 목록을 폐기하지 않는 추가 추적 항목이다. 전체 목록의
완료 수를 올리는 것이 아니며 기존 상충 항목은 아래 기준과 대조해 재분류한다.

- **AC-CON-01:** 검증된 Connector에서 원본 수신·지속 보존·중복 제거·순서 관리가
  동작하며 미연결/누락/불확실 상태가 사실대로 보인다.
- **AC-CON-02:** 메시지 수신만으로 Lead/AI/설계 수정·CTO/Worker 실행이 시작되지 않는다.
- **AC-CON-03:** 사용자의 명시적 분석 시작은 해당 시점 원본 범위를 고정하고,
  새 수신이 그 범위나 기존 승인 Revision을 몰래 바꾸지 않는다.
- **AC-CON-04:** 초기 상담 분석→요구/초기 설계→사용자 협의→UI 설계→Baseline
  승인 흐름과 해당 원본·결정·Revision 연결이 실제 검증된다.
- **AC-CON-05:** Baseline 이후 입력은 기존 설계를 덮어쓰지 않고 Lead의 세 분류와
  근거로 추적된다. 분류는 승인이나 실행 권한을 대신하지 않는다.
- **AC-CON-06:** CR 영향에 요구/UI/기술/CTO Workstream/Task/일정/상품 범위가
  포함되고 UNKNOWN이 무영향으로 처리되지 않는다.
- **AC-CON-07:** 승인된 변경만 새 Revision으로 발행·실행되며 무영향 작업과
  기존 승인·원문·검증 이력이 보존된다.
- **AC-CON-08:** Connector 재연결/중복/역순/부분 실패와 분석 중 수신·재시도,
  Workspace 교차 접근·미승인 실행을 시험한다. 자동 검사와 실제 연동 증거를 구분한다.

## 7. 이전 문서·작업과의 관계

- v15 §2C의 `실시간 동기화·계속 감시를 만들지 않음`, 수동 Batch만을 기본으로
  하는 정책과 AC-51의 수집 전면 금지는 이 결정이 대체한다.
- 기존 AC-45~52의 범위 미리보기·원본/순서/발신자·중복/누락·Workspace 격리·허용된
  취득 경로 원칙은 새 수집·명시 분석 단계에 맞춰 추적한다. 수신 자체에 매번
  AI 분석 승인이나 수동 Batch 명령을 요구하는 것으로 읽지 않는다.
- v0.8 D3/H.7의 지속형은 상시 AI 실행을 뜻하지 않는다. G5는 최초 Baseline
  이후 변경관리와 연결한다. 원래 v0.8 파일은 역사 원본으로 보존한다.
- Marketplace·자체 native 연결·Core Preview 보류, UI v9 구조·Builder 전용 검정
  디자인, 비공개 Core/공개 SDK 경계는 바꾸지 않는다.
- 현재 구현·독립 QA·실제 연동·앱/AI·실기기 완료 여부는 별도 증거로 판정한다.
