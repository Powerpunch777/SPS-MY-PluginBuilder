# Builder 실행·인계·QA·복구 계약 보강

기준: 2026-11-05 사용자 직접 요청. 기존 v15·CSAS·문서센터·Integration Manager·범용 권한
결정의 실행 계약을 강화한다. 설계 반영은 구현 완료나 실제 동작 검증을 뜻하지 않는다.
기존 Agent 수와 책임, 정본 저장소, 사용자 전용 결정 및 보류 범위는 유지한다.

## 1. 선행조건과 실행 경계

Builder가 역할과 업무 정책을 정의하고 Core가 범용 기술 권한을 강제한다. Lead 여섯 논리
세션·CTO·Worker·QA·별도 Integration Manager의 실제 생성/실행/재개 경로 모두에 이 경계를
적용한다. Manager만의 예외 권한이나 별도 CAO Lead를 추가하지 않는다.

Core의 실제 Agent/Session/Run/Grant/Node/Runner/Secret/Workspace 계약을 확인한 뒤 연결한다.
역할 템플릿과 승인된 Workstream/Task를 현재 Host 위임·기술 권한·적격 CLI 풀 예약에 결속한다.
Host가 승인한 범위 내 정상 실행마다 사용자에게 권한을 다시 묻지 않는다. 범위 확대·다른
Workspace·보호 자원·사용자 전용 결정은 사전 위임으로 우회할 수 없다.

필수 선행조건은 다음처럼 구분한다. 명칭은 의존성 분류이며 새로운 서비스/API 이름이 아니다.

| 의존성 | 필요한 실제 기능 | 2026-11-05 확인 수준 |
| --- | --- | --- |
| 범용 실행 위임 | 실제 Host 관리자 발급/철회, Plugin 소유 Agent와 검증 가능한 작업 결속, 실행 직전/Node claim/lease 검증 | 구현 중. 역할 문서·기본 프로필 생성만으로 충족하지 않음 |
| 적격 CLI 풀 | 허용 범위·공급자/모델·Node/Runner·인증·동시성에 따른 단일 예약 권위와 비밀 비노출 | 기존 계정 선택/Node 실행 기반은 있으나 전체 연결 검증 없음 |
| 보호 TestPlan | 승인된 실행 명세와 실제 Source/파일/프로세스/자손/Secret 보호, 취소 및 정리 | 범용 보호 실행은 미완성. validator·고정 CLI dispatch·fixture를 대체 증거로 쓰지 않음 |
| 실제 실행 증거 | Task/Revision/commit/artifact/환경과 실제 Run/결과를 권위 있게 조회 | Builder Gate의 성공 경로 연결이 아직 미검증 |
| Commit·Artifact 인계 | 검증 가능한 저장소·Commit 및 완전한 의존 closure, 불변 산출물 조회와 소비 권한 | 일부 현행 개발 QA는 snapshot-only이며 최종 Commit QA 조건을 충족하지 않음 |

없는 계약을 API로 주장하거나 caller boolean/fixture reader로 우회하지 않는다. 미구현은
담당·차단 기능·다음 해소 조건을 가진 선행 의존성으로 기록하며 독립 기능은 계속 진행한다.
권한 API와 Workspace 식별만으로 CLI의 OS 파일 접근이 격리된다고 주장하지 않는다.
공용 풀의 상태 조회·전환도 실제 Host 정책과 공급자 허용 범위를 따라야 한다.

## 2. 기존 Task Packet의 인계 계약

기존 Task Packet·Workstream·Revision/CAS·Artifact·테스트 증거의 참조를 확장한다.
별도 작업 원장/큐/승인 DB를 만들지 않는다. 아래는 필수 의미이며 실제 필드명은 현재
저장·공개 SDK 계약에 맞춘다. 문자열이 있다는 사실이 대상 존재·권한·현재성을 증명하지 않는다.

| 묶음 | 인계마다 유지할 참조 |
| --- | --- |
| 작업 정체성 | Workspace/프로젝트, Workstream ID, Task ID, Packet ID/버전/해시, 생산자·소비자와 실제 Agent/Run |
| 승인 기준 | 승인 Baseline/Spec/UI/Workstream Revision, 필요한 Gate/위임·정책 버전 |
| 소스 | 저장소 식별, 입력 Commit SHA, 결과 Commit SHA, tree/소스 해시, 적용 브랜치/후보, 변경 경로와 의존 closure |
| 산출물 | Artifact ID/버전/해시, manifest, 실제 조회 경로와 소비 권한, 필요한 라이선스/출처 |
| 검증 | TestPlan ID/버전/해시, QA 실행 ID, 검사 Commit/tree, 환경 참조, 결과·로그/증거 ID, 미검증 범위 |
| 전달·복구 | handoff/event/request/attempt ID, 멱등 키, 선행 산출물 버전, 전달/인수 시각, 실패 사유와 다음 조치 |

개발 착수 전에는 결과 Commit/QA가 아직 없을 수 있다. 이때 입력 Commit은 고정하고 결과는
`미생성`으로 명시한다. 결과를 만든 것처럼 SHA를 채우지 않는다. Worker 제출과 CTO 검증 완료,
최종 QA/통합 인수에는 실제 결과 Commit과 산출물·증거가 필요하다.

생산자 완료와 소비자 인수는 분리한다.

1. 생산자는 승인 범위의 결과 Commit/Artifact와 완전한 closure를 발행하고 불변 인계 참조를 남긴다.
2. 소비자는 실제 권한으로 결과를 읽고 scope/Revision/해시/의존성과 자신의 입력 계약을 확인한다.
3. 읽기·검증 후 기존 Revision/CAS 기록에 인수 또는 거절·대기를 남긴다. 채팅 수신/접수는 인수가 아니다.
4. 응답 유실·재전달은 같은 인계 ID/버전의 기존 결과를 반환하며 작업을 중복 생성하지 않는다.
5. 소비 대상 버전이 바뀌면 새 인계로 연결하고, 과거 성공/실패·거절 이유는 보존한다.

소스는 Commit/불변 Artifact와 의존 closure로 전달한다. 긴 원문 채팅, 파일별 Lead 전달,
수신 확인 대기를 정상 개발의 필수 절차로 만들지 않는다. 공급자가 빠진 type declaration,
생성물·lockfile·환경 계약도 소비 가능성을 결정하면 closure에 포함한다.
복사본으로 개발할 때 원본 editing owner는 한 명이며 소비자가 독자 정본을 만들지 않는다.

## 3. 정확한 QA 대상과 영향 범위

독립 QA는 실제 검사한 Commit/tree, 변경 경로, 의존 closure, 승인 Revision, TestPlan,
Node/OS/런타임/도구·의존 lock·필요 binary/빌드 산출물 식별과 실행 증거에 연결한다.
비밀 값·사용자 데이터·인증 경로는 환경 기록에 넣지 않는다.

- 최종 인수 QA는 실제 Commit의 불변 checkout 또는 동일 blob/tree가 검증된 대상에서 수행한다.
  혼합 WIP나 변경 중 작업 디렉터리를 최종 Commit QA로 인정하지 않는다.
- 개발 중 snapshot-only QA는 허용하되 그 한계를 표시한다. 나중에 Commit SHA를 붙이는 것만으로
  Commit QA로 승격하지 않는다. 실제 검사 bytes와 Commit blob/tree의 일치 및 관련 환경을 확인한다.
- QA용 불변 대상만 고정하고 무관한 다른 작업까지 전역 동결하지 않는다. QA 도중 source/test/build/
  dependency가 바뀌면 섞인 결과를 PASS로 발표하지 않고 해당 증거의 결속을 미확인으로 남긴다.
- 이후 변경은 기존 Graph/trace/dependency pin으로 영향 집합을 계산한다. 코드뿐 아니라 승인 설계,
  인터페이스·TestPlan·환경·도구·권한 변경도 실제 영향에 포함한다.
- 영향받은 검사만 재검증한다. 무관한 기존 QA와 이력은 보존하고, 유지 근거와 새 Revision에 대한
  적용성 판단을 연결한다. 변경 전 QA를 새 Commit에서 실행한 것처럼 다시 표시하지 않는다.
- 영향 분석 근거가 부족하면 관련 범위는 UNKNOWN/재검증 필요로 둔다. 근거 없이 무관하다고
  선언하거나, 불확실하다는 이유로 매번 전체 테스트를 반복하는 운영으로 대체하지 않는다.

## 4. 권위 있는 완료 이벤트와 자동 소비

CTO `VERIFIED`는 현재 승인 Revision·담당 scope·실제 실행/Commit/Artifact·독립 QA를 Gate가
확인한 뒤 저장한다. 기존 권위 저장 경계에서 상태와 지속 완료 이벤트를 원자적으로 결속한다.
여러 저널을 재조회한 것만으로 전역 원자성을 주장하지 않으며, 지원 공백은 기술 의존성으로 남긴다.

Manager는 저장 이벤트 ID와 Workstream/검증 Revision/Commit을 기존 cursor·CAS·lease로 소비한다.
재전송·재시작 때 같은 후보를 중복 통합하지 않고, 시작/효과 직전에 현재 권한·Gate·Revision을 확인한다.
수신/선택/통합 중/통합 완료는 CTO 검증 상태와 다른 상태다. 이벤트 전달 ACK를 통합 완료로 보지 않는다.

정상 의존 대기는 정확한 선행 Task/Artifact/계약 버전과 재개 이벤트를 기록한다. 새 생산자 결과가
도착하면 필요한 소비자만 재평가하고 무관한 작업은 진행한다. 아직 없는 다른 CTO의 전체 통합
결과를 로컬 VERIFIED의 선행조건으로 요구하지 않는다.

정상 완료는 Manager, 기술 오류는 해당 CTO, 설계·교차 계약 충돌은 Integration Review,
사용자 고유 결정만 Discussion으로 라우팅한다. 같은 상태를 반복 게시하거나 Lead를 반복 호출하지 않는다.

## 5. 제한된 재시도·관측 가능한 대기·복구

모든 Agent 실행은 승인된 Packet/Run에 재시도 횟수·총 시간 한계, 시도 ID, 실제 실패 분류,
다음 재시도 시각 또는 재개 이벤트, 복구 담당과 경로를 결속한다. 구체 수치는 기존 Core/provider
제약과 Task 위험에 맞춰 CTO가 정한다. 숨은 retry 계층이 총 한계를 늘리지 못하게 한다.

구현 상태명은 기존 것을 재사용하되 최소한 다음 의미를 구분한다.

| 의미 | 관측과 재개 |
| --- | --- |
| 정상 의존 대기 | 어떤 생산자·버전을 기다리는지, 최근 관측/다음 조건, 정체 검토 시점 |
| 권한/프로필/슬롯 대기 | 누락·철회·만료·인증·한도·동시성 사유와 실제 관리자/기술 해소 경로 |
| 재시도 예약 | 실패 분류, 소모한 예산, 다음 시각, 동일 작업/이전 attempt 연결 |
| 실행 중 | 실제 Run/lease·진행 관측. 응답 timeout을 즉시 프로세스 사망으로 취급하지 않음 |
| 복구/종료 확인 중 | 취소 요청과 실제 종료를 구분, 부작용·실행 생존 확인 전 중복 실행/슬롯 조기 재사용 금지 |
| 처리 필요/최종 실패 | 자동 복구 한계 도달, 담당·원인·보존 결과·다음 결정. 정상 대기로 숨기지 않음 |

한도·일반 오류·권한 거부·실행환경 장애를 구분한다. 같은 거부의 무한 재시도, 무단 계정/모델
변경, 인증파일 덮어쓰기, 유료 초기화는 금지한다. 실패와 미검사 결과를 보존한다.
대기에는 정체 감지 한계와 후속 조치가 있어야 한다. 한계 도달 시 기술 담당에게 한 번 올리고
동일 상태 반복 알림을 억제한다. 의존 대기를 임의 성공/실패로 바꾸거나 정상 실행을 timeout만으로 죽이지 않는다.

재시작 시 기존 요청/attempt·지속 이벤트 cursor·예약/lease·인계 인수를 복구한다. 효과가
확정되지 않은 Git 작업/외부 호출은 상태 확인 없이 재생하지 않는다. 철회는 신규 실행을 막고
진행 실행을 Core 정책에 따라 취소하되 실제 종료 확인까지 불확실성을 유지한다.

## 6. 속도 관측

새 모니터링 시스템을 만들지 않고 기존 Task/Run/Revision/이벤트의 시각·상태 전이를 사용한다.
Workstream/Task와 승인 Revision별로 다음을 기록한다.

- 승인된 작업의 준비→착수→Worker 제출→QA 인수/완료→Manager 인수/통합 완료의 실제 경과 시간.
- 권한 대기, 의존/통합 대기, 프로필/슬롯 대기와 실제 실행 시간.
- 재작업 횟수·시간과 원인: 제품 변경, 결함, source drift, 누락된 생산자/closure, 환경 장애 등.
- 계획된 사용자 결정과 불필요한 수동 개입을 구분한 횟수·사유. 수동 소스 전달/재배정/권한
  반복 요청/실행 복구를 별도 분류한다. 사용자 답변 내용이나 비밀은 수집하지 않는다.

병렬 시간 구간을 단순 합산해 전체 소요 시간으로 표시하지 않는다. 누락 시각은 미측정으로
남기고 추정치로 채우지 않는다. 테스트 통과 수는 품질의 부분 증거이지 개발 속도나 제품 완료율이 아니다.

## 7. 최종 종단 간 인수

단위/fixture와 분리된 실제 Builder 앱·Core·SDK·Node/CLI 경로에서 수행한다. 실제 운영 데이터
대신 격리된 인수 Workspace/저장소를 쓰고, 계정/Host 위임은 실제 승인 범위에서만 사용한다.
추가 OS/설치/네트워크 효과가 필요하면 기존 실험 동의를 일반화하지 말고 범위를 확인한다.

1. 실제 Host 관리자 사전 위임 후, 동일 승인 Revision의 독립 Workstream 두 개를 서로 다른
   CTO가 병렬 수행한다. 각각 별도 Worker가 실제 코드를 제출하고 CTO가 결과 Commit을 만든다.
2. 구현자와 독립된 QA가 두 실제 Commit과 환경을 확인하고 TestPlan을 실행한다. 인계/인수 기록,
   실제 동시 실행 구간과 관련 증거를 남긴다. 정상 흐름의 불필요한 사용자 개입은 0회여야 한다.
3. 권위 Gate의 긍정 VERIFIED 저장 이벤트가 Manager를 자동 실행시키고, 준비된 결과를 실제
   후보 브랜치로 통합해 CI/E2E를 수행한다. 사람이 이벤트를 대신 넣거나 통합 명령을 대행하면
   자동 경로 통과로 인정하지 않는다. Final Packet 이후 Main/G7/사용자 최종 승인 경계는 유지한다.
4. 작업 실패: 한 Worker 실패 뒤 제한 내 재시도/CTO 환류, 다른 Workstream의 계속 진행,
   원본 실패 보존과 한계 도달 시 처리 필요 전환을 검증한다.
5. 권한 철회: queue/claim/실행 중 각각 신규 차단·재검사·취소/실제 종료 확인·슬롯 보호를 검증한다.
6. 소스/설계 변경: QA 또는 통합 전 관련 Commit/Revision을 바꾸고 stale 인수 차단,
   영향 범위만 재검증, 무관한 QA/승인 이력 보존을 검증한다.
7. 프로세스 재시작/응답 유실/중복 전달: cursor/인수/lease 복구와 통합·외부 효과의 중복 방지를 검증한다.
8. 생산자 지연: 정상 의존 대기와 실행 오류의 구분, 자원 해제, 정체 감지, 생산자 완료 후
   소비자 자동 재개, 같은 상태의 반복 Lead/사용자 호출 억제를 검증한다.

각 결과는 대상 Commit/환경/실제 실행·이벤트·산출물·오류 주입 지점과 함께 PASS/FAIL/
BLOCKED/NOT_RUN을 기록한다. Core 선행 공백으로 못 실행하면 BLOCKED이며 mock 성공으로 대체하지 않는다.
현재 위 전체 시나리오는 NOT_RUN이다. 기존 임시 CAO 병렬 개발 성공도 제품 인수의 대체 증거가 아니다.

## 9. 공용 풀 전환과 저장 세션 재개

2026-11-05 후속 사용자 결정: 계정 전환은 저장된 CLI 대화를 이어가는 방식이 기본이다.
대량의 복구 지시문으로 새 대화를 만드는 절차와 구분한다. 임시 CAO 수정이 Builder 정식
엔진의 채택이나 Core 기능 구현 완료를 뜻하지 않는다. 아래는 기존 POLICY-EXEC-02/09/11/15의
재개 인수 조건이며 별도 Agent·권한 체계·세션 원장을 추가하지 않는다.

1. 기존 Core Agent/Session/Run과 Task의 실행 의도, 실제 실행 상태, 사용자 중단 상태를 구분한다.
   전환 직전에 실제 활성 세션·부모/자식·Task·승인 Revision·CLI thread·lease 결속을 고정하고
   저장 대화의 재개 가능성과 대상 프로필의 적격성을 확인한 뒤 중단한다. 미확인 상태에서
   먼저 전체를 멈추거나 과거 Agent 목록 전체를 재개 대상으로 삼지 않는다.
2. 자동 전환은 그때 활성인 세션만 대상으로 한다. 사용자 중단·비활성·완료 세션은 그대로
   보존한다. 활성 자식의 부모가 비활성이라면 부모까지 임의 활성화하지 않고, 지원되는
   정당한 부모 결속 또는 처리 필요 상태로 분리한다. 권위 있는 활성 기록이 없는 장애 후
   복구는 자동 추측하지 않고 명시적인 대상 선택으로 처리한다.
3. 사용자가 중단 세션의 재개를 요청하면 현재 선택된 적격 계정으로 해당 세션만 이어갈 수
   있어야 한다. 이전 계정으로 되돌아가거나 다른 중단 세션까지 깨우지 않는다. 현재 역할,
   Task/Workstream, 승인 Revision, 모델·도구·경로·Host 위임을 재검증하며 과거 대화가 현재
   권한을 부여하지 않는다. 변경된 설계는 원본 참조로 확인하고 관련 범위만 조정한다.
4. 저장 CLI thread ID와 대화 이력은 유지하되 새 프로세스·Run/lease·attempt 및 부모/메시지
   라우팅을 결속한다. 종료 확인 전 중복 시작, 불확실한 외부 효과 재생, 같은 활성화 요청의
   중복 소비를 막는다. 루트가 작업자를 중복 생성하지 않도록 기존 자식 연결을 먼저 확정한다.
5. 인증은 Core가 선택한 기존 적격 풀에서 사용하고 Secret/인증파일은 Agent에 노출하거나
   복사·덮어쓰지 않는다. 공급자·CLI가 저장 이력을 다른 적격 계정에서 재개하는 지원 경로를
   실제 확인한다. 지원이 없으면 BLOCKED로 알리고 새 대화나 이력 누락을 같은 세션 재개로
   표시하지 않는다. 계정 자동 전환은 승인된 범위·재시도 예산 안에서만 수행한다.
6. 시스템 화면은 요청 접수, 전환 준비, 종료 확인, 저장 대화 재연결, 실제 AI 수행, 실패·처리
   필요를 구분하고 이전/현재 계정의 비밀 없는 식별과 대상·제외 세션을 보여준다. thread ID
   일치만으로 대화 이력·도구 라우팅·실제 수행이 검증됐다고 표시하지 않는다.

인수에는 서로 다른 적격 계정의 실제 전환, 활성/중단/완료 혼합 집합, 중단 세션의 나중 개별
재개, 자식 라우팅, 만료·철회·중복 요청·재시작·이력 접근 실패를 포함한다. 실제 실행 검증은
현재 NOT_RUN이며 로컬 가짜 이력 검사나 CAO 운영 복구와 별도로 보고한다.
