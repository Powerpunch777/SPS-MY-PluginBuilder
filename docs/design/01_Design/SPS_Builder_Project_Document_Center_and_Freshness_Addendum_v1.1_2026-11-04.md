## 0. CAO Lead 질의에 대한 답변 및 결정

**질의 요지:** 설계 문서·검증 기준·UI 설계·기술 조사·작업 명세 등 문서가 많아지면 AI는 읽기 쉬워도 사용자가 프로젝트 현황을 파악하기 어려울 수 있다. 현재 UI에 문서만 모아 분류·정렬·열람하는 화면이 있는가? 문서를 최신 상태로 계속 유지할 수 있는가?

**답변 및 결정:**

1. 기존 UI 설계에는 문서 전체를 별도로 모아 탐색·정렬·열람하는 전용 화면이 명확히 정의되어 있지 않다. 따라서 프로젝트 좌측 탐색에 **「문서」(Project Document Center)** 진입점을 추가하고, 중앙 작업영역에 독립적인 문서 관리 화면을 제공한다.
2. 문서 센터는 새로운 AI 세션이 아니라 기존 프로젝트 데이터와 Artifact를 사용자가 읽고 검토하는 화면이다. 기존 Lead 5개 세션, CTO/Worker 영역, 미결정사항 패널, HTML UI 뷰어의 역할을 대체하거나 훼손하지 않는다.
3. 문서는 상담 자료, 설계 문서, UI 설계, 검증 기준, 기술 조사, 개발 작업, 변경 이력, 테스트·QA, 납품·사용법 등으로 분류한다. 제목·본문 검색, 유형·승인 상태·최신성 필터, 수정일·제목·Revision 정렬을 제공한다.
4. 사용자가 모든 세부 파일을 직접 읽어야 하는 구조는 피한다. 하나의 **통합 설계 기준선 문서**를 제공하고, 개별 요구사항·검증 기준·UI Contract·Task·QA 증거는 통합 문서에서 필요한 경우에만 열어볼 수 있도록 연결한다. AI 내부의 세분화된 구조화 데이터와 사용자가 읽는 통합 문서는 분리한다.
5. 문서 최신성은 AI에게 주기적으로 모든 문서를 다시 작성하게 하는 방식이 아니라, 정식 프로젝트 데이터의 Revision과 문서 간 추적 관계를 기준으로 관리한다. 원본 데이터나 승인된 기준이 바뀌면 영향받는 문서만 검토 필요 상태로 표시하고 새 Draft/Revision을 만든다.
6. 문서의 **승인 상태와 최신성 상태는 별도로 관리**한다. 과거 승인 문서는 변경이 발생해도 승인 이력을 보존하며, `APPROVED + REVIEW_REQUIRED`처럼 승인 사실은 유지하면서 현재 기준과의 재검토 필요성을 표시한다.
7. 승인된 Design Baseline과 과거 Revision은 자동으로 덮어쓰지 않는다. 변경 승인 전에는 기존 기준선을 유지하고, 승인 후 새 Revision을 발행한다.
8. 상담 메시지가 실시간으로 수집되는 것만으로 AI 분석이나 설계 문서를 자동 갱신하지 않는다. 사용자가 명시적으로 상담 분석을 시작하거나, Design Baseline/Change Request 등 정식 승인 이벤트가 발생했을 때만 해당 절차에 따라 산출물을 갱신한다.
9. 최신성 여부를 판단할 근거나 연결 관계가 부족하면 AI가 임의로 최신이라고 선언하지 않고 `UNKNOWN` 또는 `REVIEW_REQUIRED`로 표시한다.

**사용자 관점의 최종 원칙:** 문서와 내부 데이터는 많아져도 사용자가 확인할 공식 기준은 통합 Design Baseline 하나를 중심으로 유지한다. 세부 문서는 필요할 때만 열어보며, 모든 문서의 승인 상태·최신성·근거·변경 이력을 문서 센터에서 확인할 수 있어야 한다.

## 1. 목적과 사용자 문제

Builder의 설계·개발 과정에서 다음과 같은 문서와 산출물이 계속 생성된다.

- 고객 상담 원문 및 수집 기록
- 요구사항 명세와 통합 설계 문서
- Design Baseline 및 Revision
- HTML UI 시안, UI Contract, UI Revision
- 공통 검증 기준, Domain Pack, 프로젝트별 검증 기준
- 기술 조사 및 기술 선정 기록
- CTO Workstream 및 Worker Task Packet
- Change Request와 영향 분석 보고서
- 테스트 계획, QA 결과, 증거 자료
- 사용법 및 최종 산출물 설명서

이 자료가 각 세션·폴더·에이전트 결과에 흩어지면 AI가 참조하기에는 편리해도 사용자가 프로젝트의 현재 상태와 승인된 기준을 파악하기 어려워진다.

따라서 프로젝트별 문서를 한곳에서 분류·검색·정렬·열람하고, 각 문서가 최신 승인 설계와 일치하는지 확인할 수 있는 **Project Document Center(프로젝트 문서 관리 센터)**를 제공한다.

이 기능은 단순 파일 브라우저가 아니라, 프로젝트의 승인된 설계와 파생 산출물을 사람이 검토·통제하는 사용자 인터페이스다.

## 2. 확정할 UI 배치

### 2.1 진입 위치

기존 프로젝트 좌측 탐색 영역에 **「문서」(Project Documents)** 진입 항목을 추가한다.

- Lead 대화 세션이나 CTO/Worker 목록과 별개의 프로젝트 기능으로 둔다.
- 문서 센터는 새 AI 세션이 아니다. 문서 열람·검색·상태 확인을 위한 화면이다.
- 기존 미결정사항 패널과 HTML UI 뷰어의 목적 및 동작은 유지한다.
- 문서 센터를 열어도 Main, UI Design, Background, Question Intake, Question Discussion의 역할과 세션 구성을 변경하지 않는다.
- 신규 Builder의 최초 개발 범위에는 기존 3세션 사용자 마이그레이션·이전 대화 메뉴를 추가하지 않는다.

### 2.2 화면 구성

문서 센터는 중앙 작업영역에 표시한다. 화면 내부는 다음 3영역을 기본안으로 한다.

1. **문서 분류 영역:** 문서 카테고리 및 저장된 필터
2. **문서 목록 영역:** 제목, 유형, 버전, 승인 상태, 최신성, 수정 시각
3. **문서 미리보기/상세 영역:** 문서 본문, 출처, 연결 관계, Revision, 변경 이력, 승인 근거

기존 제품의 전역 우측 미결정사항 영역과 충돌하지 않도록, 문서 상세 메타데이터는 문서 센터 내부 패널 또는 상세 탭으로 구성한다. 실제 레이아웃은 Core의 Workspace Shell/viewport 계약을 확인한 후 확정한다.

### 2.3 기본 와이어프레임(개념)

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 프로젝트 문서                                      검색 [_________] │
├─────────────────┬────────────────────────────┬──────────────────────┤
│ 분류             │ 문서 목록                   │ 문서 미리보기/정보    │
│                 │                            │                      │
│ 전체             │ 프로젝트 통합 설계 기준선   │ 제목                 │
│ 상담 자료         │ 요구사항 명세               │ 문서 유형             │
│ 설계 문서         │ UI 설계서                   │ 버전 / Revision       │
│ UI 설계           │ 공통 검증 기준              │ 승인 상태             │
```

이는 개념 배치이며 픽셀·컴포넌트·반응형 구현을 확정하는 UI 시안은 아니다.

## 3. 문서 분류 체계

문서 센터는 다음 기본 분류를 제공한다. 실제 저장소의 기존 문서 유형과 중복되는 별도 파일 체계를 만들지 말고, 기존 Artifact/Specification/Revision 모델을 재사용한다.

| 분류 | 포함 자료 | 주요 사용자 목적 |
|---|---|---|
| 상담 자료 | 플랫폼 대화 원문, 수집 이력, 상담 분석 결과 | 고객이 실제로 말한 내용 확인 |
| 설계 문서 | 프로젝트 개요, 요구사항, 통합 설계, Design Baseline | 현재 승인된 제품 범위 파악 |
| UI 설계 | HTML 시안, UI Contract, UI Revision | 화면·동작 설계 검토 |
| 검증 기준 | 공통 기준, Domain Pack, 프로젝트별 기준, Acceptance Criteria | 무엇을 어떤 방법으로 검증할지 확인 |
| 기술 조사 | 재사용 조사, OSS 비교, 기술 결정 기록 | 기술 선택 근거 확인 |
| 개발 작업 | Workstream, Task Packet, 인터페이스 계약 | CTO/Worker의 작업 범위 확인 |
| 변경 이력 | Clarification, Correction, Change Request, 영향 분석, Revision diff | 무엇이 왜 바뀌었는지 확인 |
| 테스트·QA | 테스트 계획, 실행 결과, QA 보고서, 증거 | 구현이 실제로 검증됐는지 확인 |
| 납품·사용법 | 패키지 목록, 사용법, 최종 검증 결과 | 사용자가 최종 결과를 확인 |

문서 분류는 논리적 분류/태그로 관리할 수 있으며, 모든 항목이 물리적으로 별도 파일이어야 하는 것은 아니다.

## 4. 사용자가 보기 쉬운 통합 문서와 AI용 세부 데이터의 분리

### 4.1 원칙

**AI 내부에서 사용하는 구조화 데이터와 사용자가 열람하는 문서를 1:1로 만들지 않는다.**

예를 들어 AI 내부에는 개별 Requirement, Validation Criterion, UI Component, Technology Decision, Workstream, Task, Test Evidence가 각각 독립 ID와 관계로 저장될 수 있다.

사용자에게는 이들을 통합한 읽기 쉬운 문서와 요약 화면을 제공한다.

### 4.2 통합 설계 문서

프로젝트별로 다음 항목을 포함하는 **통합 설계 기준선 문서**를 제공한다.

1. 프로젝트 개요 및 외주 상품 범위
2. 고객 요구사항 및 요구사항별 근거
3. 기능·동작·데이터·권한 설계
4. UI 설계 및 승인된 시안 링크
5. 공통·Domain·프로젝트별 검증 기준 요약
6. 기술 선정 및 재사용 결정 요약
7. CTO Workstream 및 주요 의존관계
8. 주요 미결정사항과 승인된 결정
9. 변경 이력 및 현재 Baseline 상태

세부 검증 기준, UI Contract, Task Packet 등은 통합 문서 안에 전부 복제하지 않고 링크/참조로 연결한다. 사용자는 요약을 먼저 읽고 필요한 세부 문서만 열람할 수 있어야 한다.

### 4.3 문서 생성 방식

- 통합 문서는 정식 데이터와 승인된 Revision을 기반으로 생성·갱신되는 읽기용 View/Artifact로 취급한다.
- 동일한 내용을 여러 문서에 수동 복사해 서로 다른 버전으로 관리하지 않는다.
- Markdown을 기본 열람·내보내기 형식으로 지원한다. PDF 등 추가 내보내기는 기존 제품 범위와 구현 비용을 확인해 결정한다.
- AI가 작성한 임시 메모나 세션 응답이 자동으로 승인된 정식 문서가 되지 않는다.

## 5. 문서 최신성 유지 설계

### 5.1 핵심 답변

문서를 최신 상태로 유지할 수 있다. 단, **AI에게 문서를 계속 알아서 고치라고 지시하는 방식이 아니라, 정식 데이터의 Revision과 문서 간 의존관계를 기준으로 갱신·무효화하는 방식**으로 구현해야 한다.

문서 센터가 보여주는 최신성은 '가장 최근에 AI가 작성한 문서'가 아니라 **현재 승인된 프로젝트 기준선 및 관련 원본과의 정합성**을 의미한다.

### 5.2 단일 기준 데이터(Single Source of Truth)

정식 정보는 기존 프로젝트 데이터 모델을 기준으로 관리한다.

- 원본 상담 메시지 및 외부 플랫폼 이벤트
- Requirement 및 Requirement-to-Source Trace
- Decision 및 승인 근거
- Product Specification / Design Baseline / Revision
- UI Contract / UI Artifact / UI Revision
- Validation Criteria / Domain Pack 적용 기록
- Technology Decision
- Workstream / Task Packet
- Change Request / Impact Report
- Test Run / QA Evidence / Package Artifact

문서 파일은 이 데이터의 읽기용 표현 또는 특정 시점의 승인 스냅샷이다. 동일한 사실을 문서 파일 여러 곳에서 독립적으로 수정하도록 만들지 않는다.

실제 Entity/DB/API 이름은 기존 Core·SDK 및 Builder 구현 계약을 확인한 뒤 결정한다. 위 목록은 논리적 책임 범위이지 신규 테이블 이름을 강제하는 명세가 아니다.

### 5.3 이벤트 기반 갱신 흐름

| 발생 이벤트 | 문서 센터 동작 |
|---|---|
| 상담 메시지 수집 | 상담 원문/수집 상태만 갱신. AI 분석·설계 문서를 자동 변경하지 않음 |
| 사용자가 상담 분석 시작 | 상담 분석 초안 및 요구사항·근거 연결 초안 생성 |
| 사용자가 설계 초안 수정 | 관련 Draft 문서와 미리보기 갱신 |
| Design Baseline 승인 | 승인된 Baseline 스냅샷 생성·고정, 관련 통합 설계 문서 갱신 |
| UI 시안/Contract 승인 | 해당 UI Revision 및 연결 문서 갱신 |
| 검증 기준 승인 | 승인된 기준 묶음과 적용 대상/버전 갱신 |
| Change Request 접수 | 변경 제안·영향 분석 Draft 생성. 기존 승인 문서는 덮어쓰지 않음 |
| Change Request 승인 | 새 Spec Revision 발행, 영향받는 문서만 새 Draft/Revision으로 갱신 |
| CTO Workstream/Task 변경 | 해당 작업 문서와 연결된 통합 요약 갱신 |
| 테스트/QA 완료 | 테스트·증거 문서 및 인수 상태 갱신. 설계 기준선 자체는 수정하지 않음 |

메시지 수집 이벤트가 문서 전체의 재작성이나 AI 상담 분석을 자동 유발해서는 안 된다. 상담 분석은 사용자의 명시적 실행으로 시작한다.

### 5.4 최신성 상태와 승인 상태 분리

문서의 **승인 상태**와 **최신성 상태**는 별개의 축으로 관리한다.

**승인 상태 예시**

- `DRAFT`: AI/담당 세션이 작성한 초안
- `IN_REVIEW`: 사용자 검토 대기
- `APPROVED`: 권한 있는 사용자가 승인
- `SUPERSEDED`: 새 Revision으로 대체
- `ARCHIVED`: 보관

**최신성 상태 예시**

- `CURRENT`: 현재 기준선 및 연결된 원본과 정합
- `REVIEW_REQUIRED`: 연결된 원본이 변경되어 검토 필요
- `STALE`: 기준선/참조 버전과 불일치하거나 오래된 자료
- `UNKNOWN`: 연결 관계 또는 최신성 판정 근거 부족

예: `APPROVED + REVIEW_REQUIRED`는 과거에 정식 승인된 문서지만 관련 요구사항이 변경되어 현재 상태에서 재검토가 필요하다는 뜻이다. 기존 승인 기록을 삭제하거나 승인 사실을 소급 취소하지 않는다.

### 5.5 영향받는 문서만 갱신

- Requirement/Decision/UI/Validation/Task 사이의 추적 관계를 활용해 변경 영향 범위를 계산한다.
- 변경과 관계없는 문서는 `CURRENT`를 유지한다.
- 연결이 누락되거나 영향 범위를 확정할 수 없으면 `UNKNOWN` 또는 `REVIEW_REQUIRED`로 표시하고 AI가 임의로 최신이라고 판정하지 않는다.
- 영향받은 문서는 새 초안/Revision을 생성한다. 승인된 기존 문서를 조용히 덮어쓰지 않는다.
- 사용자 승인 전에는 새 초안이 공식 Baseline을 대체하지 않는다.

### 5.6 문서별 최신성 메타데이터

각 문서/Artifact에 최소한 다음 정보를 연결한다. 필드명은 예시이며 실제 스키마는 기존 계약에 맞춘다.

- 문서 ID 및 문서 유형
- 프로젝트 ID / Workspace ID
- 문서 Revision 또는 Artifact Version
- 참조하는 Design Baseline/Spec Revision
- 연결된 Requirement/Decision/UI/Validation/Task ID
- 생성·수정 시각
- 작성 주체(Lead/세션/CTO/Worker/사용자)
- 승인 상태 및 승인 근거
- 최신성 상태와 stale 사유
- 원본 출처 및 콘텐츠 해시(파일형 Artifact인 경우)

문서 상세 화면에는 “어떤 승인 Revision을 기준으로 작성됐는지”, “왜 검토가 필요한지”, “어떤 변경으로 stale이 되었는지”를 사람이 이해할 수 있게 보여준다.

## 6. 문서 탐색·검색·정렬 기능

초기 구현에서 다음을 지원한다.

- 제목 및 본문 검색
- 문서 분류별 필터
- 문서 유형별 필터
- 승인 상태별 필터
- 최신성 상태별 필터
- 최신 수정순/오래된 순
- 제목순
- 문서 유형순
- Revision순
- 관련 Requirement/Change Request/Workstream 기준 필터
- 승인된 문서만 보기
- 검토 필요 문서만 보기
- Draft 문서만 보기

문서 목록의 기본 정렬은 사용자가 최근에 수정한 순으로 할 수 있지만, `최신 문서`라는 표현은 단순 수정 시각이 아니라 승인 Revision과 최신성 상태를 함께 표시해야 한다.

## 7. 문서 간 연결과 변경 이력

문서 상세 화면에서 다음 연결을 따라갈 수 있어야 한다.

```text
상담 원문 메시지
   ↓ 근거
요구사항(Requirement)
   ↓ 구현/표현
기능 명세 · UI Contract · 승인 HTML
   ↓ 검증
공통 기준 · Domain 기준 · 프로젝트별 기준
   ↓ 배정
CTO Workstream · Worker Task
   ↓ 증거
Test Run · QA Evidence
   ↓ 결과
최종 산출물 · 사용법
```

문서 상세에서 연결된 문서로 이동할 수 있어야 하며, 관련 문서의 승인 상태·최신성 상태를 함께 확인할 수 있어야 한다.

Revision 비교는 다음을 지원한다.

- 이전/현재 Revision 비교
- 추가·삭제·수정된 요구사항
- 검증 기준의 추가·변경·제외 및 제외 사유
- UI Contract/HTML Artifact 변경
- 연결된 Workstream/Task 영향
- 승인자·승인 시각·근거
- 테스트 및 QA 증거의 유효성

## 8. 역할별 문서 작성·수정 권한

문서 센터는 공통 열람 지점이지 모든 AI 세션이 모든 정식 문서를 자유롭게 수정하는 장소가 아니다.

| 역할 | 문서 처리 책임 |
|---|---|
| Main | 상담 분석 초안, 요구사항·제품 설계의 정식 개정 경로 |
| UI Design | UI 시안·UI Contract 변경 제안 및 UI Artifact 작성 |
| Background | 기술 조사·재사용·Workstream 분할 후보 작성 |
| Question Intake | 원문/승인 기준 조회 및 CTO 질문의 근거 답변 기록 |
| Question Discussion | 사용자 답변·결정 근거 기록, Main의 승인 경로에 연결 |
| CTO | 담당 Workstream/Task, 테스트 계획 및 기술 산출물 작성 |
| Worker | 배정된 Task 산출물 및 실행 증거 작성 |
| QA | 테스트 결과와 독립 검증 증거 작성 |
| 사용자 | Design Baseline, UI 기준, 검증 기준 및 변경 요청 등 제품 결정 승인 |

Main의 정식 Specification/Revision 발행 권한과 사용자 승인 권한을 구분한다. UI Design/Background/CTO/Worker의 결과는 정해진 경로로 제안·제출하며, 승인된 기준선을 직접 덮어쓰지 않는다.

## 10. 구현 원칙과 금지사항

1. 기존 Core/SDK의 Workspace Shell, Plugin UI, 파일/Artifact 저장, 권한, 이벤트 및 Revision 계약을 먼저 확인한다. 문서 센터를 위해 별도의 중복 문서 DB를 임의로 만들지 않는다.
2. 문서 센터는 기존 설계 데이터와 Artifact를 모아 보여주는 기능이다. 새로운 Lead 세션이나 독립적인 설계 권한 계층으로 만들지 않는다.
3. 최신성 관리는 정식 데이터 Revision과 추적 관계에 기반한다. 주기적으로 모든 문서를 AI에게 다시 쓰게 하는 방식은 기본 설계로 채택하지 않는다.
4. 승인된 문서는 불변 스냅샷으로 보존한다. 최신 데이터에 맞춰 갱신이 필요하면 새 Draft/Revision을 생성한다.
5. 상담 수집은 원문 저장만 수행한다. 사용자 명시적 분석 시작 전 자동 분석·요구사항 추출·설계 갱신을 하지 않는다.
6. Design Baseline 이후 추가 요구는 기존 Change Management 흐름을 따른다. 변경 승인 전 기존 승인 문서를 덮어쓰지 않는다.
7. 문서 수, 페이지 수, 세부 기준 수가 많다는 이유로 사용자가 모든 세부 문서를 직접 읽어야 하는 구조를 만들지 않는다. 통합 설계 요약과 세부 링크를 제공한다.
8. 문서 센터의 화면 존재만으로 문서 최신성이 보장되는 것은 아니다. `AC-DOC-07~13`의 자동 상태 계산과 이벤트 기반 무효화가 검증되어야 한다.
9. AI가 문서의 최신성·승인·검증 통과를 스스로 선언하지 않는다. 승인 주체와 실행 증거를 분리한다.
10. 문서 내보내기 파일은 특정 시점의 스냅샷으로 표시하고, 원본 문서/Revision 링크와 생성 시점을 포함한다.

아래 지시를 기존 Builder 통합 설계 작업에 포함한다.

>
> 문서 센터는 별도 AI 세션이 아니라 기존 공통 프로젝트 데이터와 Artifact를 열람하는 사용자 통제 화면이다. 기존 Lead 5개 세션, 미결정사항, HTML UI 뷰어의 책임과 위치를 훼손하지 않는다.
>
> AI 내부의 구조화된 Requirement/Decision/Validation/UI/Task/Test 데이터와 사용자가 읽는 통합 설계 문서를 분리한다. 사용자는 통합 설계 요약을 먼저 읽고 필요한 세부 문서로 이동할 수 있어야 한다.
>
> 문서 최신성은 정식 데이터의 Revision과 문서 간 의존관계로 관리한다. 원본 변경 시 영향받는 문서만 검토 필요 상태로 만들고, 승인된 문서를 자동 덮어쓰지 않는다. 승인 상태와 최신성 상태를 별도 필드/상태로 관리한다.
>
> 상담 메시지 수집만으로 AI 분석이나 설계 문서 갱신을 자동 실행하지 않는다. 사용자의 명시적 상담 분석 시작, Design Baseline 승인, Change Request 승인 등 명시된 이벤트에 따라 문서/Revision을 갱신한다.
>
> 구현 전 기존 Core·SDK·Builder의 Artifact/Revision/권한/Workspace Shell 계약을 조사하고, 재사용 가능한 기능과 신규 구현 범위를 보고한다. AC-DOC-01~16을 기존 인수 기준 추적표에 중복 없이 편입한다.
>
> 이 문서만을 근거로 기존 GitHub 코드를 이미 수정했다고 보고하지 않는다. 설계 통합, 구현, 테스트, PR 반영 상태를 각각 증거로 보고한다.

## 12. 미확정 기술 세부사항

다음은 제품 요구사항이 아니라 구현 검토 후 정할 기술 세부사항이다.

- 기존 Builder의 문서/Artifact 저장소를 재사용할지, Core 제공 저장소를 사용할지
- 문서 목록/검색 인덱스의 구현 방식
- Markdown 렌더링 및 PDF 내보내기 지원 범위
- 최신성 상태 계산을 이벤트 핸들러와 백그라운드 검증 중 어디에 둘지
- 대용량 상담 원문 및 첨부파일의 검색/권한 모델
- 실제 Core/SDK의 UI Shell에 맞는 패널·탭·라우팅 구현

기술 세부사항을 결정할 때 기존 계약과 오픈소스를 우선 조사하고, 근거 없이 별도 시스템을 중복 구현하지 않는다.
