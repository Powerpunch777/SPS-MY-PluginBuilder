# Builder 현재 통합 제품 계약

기준일: 2026-11-05. 사용자 확정 결정을 통합한 현행 제품 기준이다.
새 정책을 승인하거나 구현·테스트 완료를 선언하는 문서는 아니다.
원래 v15·UI v9·CSAS v0.8의 비충돌 요구는 그대로 유지한다.
문서센터·최신성 보완 v1.1, 통합 담당 추가 설계(2026-11-04), 최종 검토·승인, 범용 권한·Host 사전 위임 및 실행·인계·복구 보강(2026-11-05)과 이후 사용자 확정 결정을 함께 적용한다.

## 1. 읽는 순서와 제품 경계

제품 목표는 사용자 최신 결정, 이 통합 계약, [시스템 완료·선택적 Wake](01_Design/SPS_Builder_CLI_Pool_Completion_And_Selective_Wake_Addendum_2026-11-05.md), [실행·인계·복구 보강](01_Design/SPS_Builder_Execution_Handoff_And_Recovery_Addendum_2026-11-05.md), [범용 권한·Host 사전 위임 추가안](01_Design/SPS_Builder_Generic_Permissions_And_Host_Delegation_Addendum_2026-11-05.md), [최종 검토·승인 페이지 추가안](01_Design/SPS_Builder_Lead_Final_Review_Approval_Page_Addendum_2026-11-05.md), [통합 담당 추가 설계](01_Design/SPS_Builder_Integration_Design_20261104.md), 문서센터·최신성 v1.1, 상담·변경관리 개정,
CSAS v0.8의 유효 조항, v15의 비충돌 조항 순으로 해석한다.
실제 구현 가능성과 보안 권한은 별도로 현재 Core/SDK 계약에서 검증한다.
기술 미지원은 제품 요구를 삭제하는 근거가 아니며, 미지원/미검증으로 기록한다.

Builder는 선택형 SPS 플러그인이다. Core는 인증·Workspace·실행·저장·Node·
보안 같은 공통 기술을 제공하고 Builder는 상담·업무·역할·명세·승인·품질을 소유한다.
특정 Room/Task/CTO 구조를 Core의 필수 업무 모델로 넣지 않는다.

선택형이라는 이유로 Workspace Shell/Primary 자격을 금지하지도,
모든 Workspace에서 Builder를 필수 Primary로 지정하지도 않는다.
해당 기능의 선언·선택·해제·복구·권한은 실제 Host/SDK 계약으로 확인한다.
매니페스트 선언은 Host 권한 부여나 활성화 성공의 증거가 아니다.

비공개 Core 소스·인증정보·사용자 데이터는 공개 Builder 레포에 넣지 않는다.
임시 CAO 개발 환경과 Builder 제품 내부의 실행 엔진은 별개다.
이 대화의 Codex가 개발 Lead이며 별도의 CAO AI Lead를 중복으로 두지 않는다.
이는 제품 내부 Lead의 여섯 논리 세션 및 별도 Integration Manager와 다른 개발 운영 결정이다.
첨부 통합 설계의 제목에 남은 `초안` 표시는 이후 사용자가 직접 확정한 책임·세션·
상태·라우팅 결정을 미정으로 되돌리지 않는다. 실제 API/저장 구현은 여전히 검증 대상이다.

## 2. 끝까지 제공할 사용자 흐름

1. 필요한 Workspace에서 Builder를 선택하고 실제 사용할 Agent를 연결한다.
2. 허용된 Connector로 고객 상담 원본을 지속 수집한다. 수신은 저장·중복 제거·
   순서 관리만 수행하며 AI 분석이나 설계 수정·Worker 실행을 유발하지 않는다.
3. 사용자가 `상담 분석 시작`을 명시적으로 요청한다. 그때까지의 원본 ID·범위·
   수집 경계·해시를 분석 snapshot으로 고정하고, 실행 중 도착한 메시지는 분리한다.
4. Main이 근거를 조회해 요구사항·질문·초기 설계와 상품 후보를 작성하고 사용자와 협의한다.
5. UI Design에서 화면·흐름·HTML 시안을 검토한다. 승인 HTML, UI Contract,
   UI Revision을 요구사항과 연결한 뒤 Main의 공식 경로로 Baseline을 확정한다.
6. Background에서 기술·재사용·라이선스·전체 운영비용을 조사하고 기술 기준을 정리한다.
   설계 검토 중 예비 실현 가능성 조사는 가능하지만 제품·UI 의도를 무단 변경하지 않는다.
7. Lead가 기능·계약·의존성·인수 기준을 CTO Workstream으로 나눈다.
8. CTO가 Worker 작업과 독립 QA를 배정하고 검토·재작업·담당 커밋을 책임진다.
9. 각 CTO는 담당 개발·내부 통합·QA와 필수 검증을 마치고 체크포인트 완료를 요청한다.
   백엔드 Gate가 현재 승인 Revision과 실제 증거를 검증해 `VERIFIED` 전환을 허가한다.
10. 별도 Integration Manager가 저장된 검증 완료 이벤트로 깨어나 준비된 영역부터 통합한다.
    기술 오류는 CTO에게, 설계·교차 계약 충돌은 Lead Integration Review로 보낸다.
11. 전체 통합·E2E·회귀 검증 이후 Final Integration Packet을 Lead Main에 전달한다.
    Main은 전체 승인 설계·QA·산출물 완비를 최종 점검한다.
12. Main이 실제 납품 목록·설치·사용법·제한과 G7 정합성을 확인하고, 불변 후보 참조를 가진
    승인 요청을 기존 Integration Review의 `최종 검토·승인` 페이지에 등록한다. 해당 Workspace의
    기존 접근·승인 권한을 충족한 실제 사용자만 승인·수정 요청·보류를 선택한다.
    필수 QA/G6/G7을 서버가 확인한 경우에만 정확한 납품 패키지 버전을 확정한다.
    이미 승인한 요구·설계는 재승인하지 않는다. 고객 전달·대외 계약·결제·배포는 별개이며
    실제 고객 전달은 사용자가 수행한다.

실제 플랫폼 접근 수단이 확인되지 않았다면 Connector가 연동됐다고 표시하지 않는다.
승인 없는 스크래핑·쿠키 추출·로그인 우회를 하지 않는다. 수동 자료 입력은 보조
수단이며 새 파일 형식·제품 정책을 이 문서로 임의 확정하지 않는다.

## 3. Lead 여섯 논리 세션과 공통 기억

| 논리 세션 | 사용자 화면 | 책임과 수정 경계 |
| --- | --- | --- |
| Main | Main | 사용자 협의, 요구·명세·기준선의 공식 발행 경로 |
| UI Design | UI Design | UI 산출물·피드백·변경 제안; 제품 기준선을 독자 승인하지 않음 |
| Background | 작업 로그·산출물 | 기술/재사용·분할 후보; 승인·위임된 발행 경계를 거침 |
| Question Intake | 내부 처리 | CTO 질문과 기존 원문·결정 근거 조회; 사용자 결정을 창작하지 않음 |
| Question Discussion | 미결정사항 | Lead가 올린 사용자 결정 질문·답변과 Revision 연결 |
| Integration Review | 최종 검토·승인 + 내부 통합 검토 | 기존 통합 이슈 검토를 유지하고 Main의 G7 적격 후보를 사용자에게 제시; 실제 사용자 응답·감사 연결, AI가 대신 승인하지 않음 |

하나의 프로젝트 Lead 정체성 아래 여섯 독립 대화/실행 컨텍스트를 둔다.
Integration Manager는 Lead 밖의 별도 프로젝트 논리 세션이다. 일곱 사용자 채팅창이나
상주 CLI 일곱 개를 강제하지 않는다. Manager와 Integration Review는 필요한 이벤트에서
실행하고 유휴 시 모델 호출을 유지하지 않는다. 승인 페이지는 일곱 번째 Lead 세션이나
새 Agent가 아니라 기존 Integration Review의 사용자 인터페이스다.
좌측 Lead 영역의 기존 Main, UI Design, 미결정사항을 보존하고 `최종 검토·승인` 진입점을 추가한다.

원본 메시지는 세션별 ID와 출처를 유지하고 다른 세션에 복제하지 않는다.
필요한 원문 범위·승인 Revision·결정·상담·UI·기술·CTO 상태를 프로젝트 범위에서
검색·조회한다. 조회 가능성이 공통 수정·승인 권한을 의미하지 않는다.
원문 존재·권한·승인은 저장된 실제 근거로 확인하며 문자열 참조만으로 증명하지 않는다.

전환·재개 시 최신 승인 Revision과 관련 결정을 다시 조회한다. 화면 이동은 AI
실행을 시작하지 않는다. 오래된 결과는 CAS 또는 동등한 검증으로 최신 설계를
덮어쓰지 못하게 한다. UI/Background 제안과 Main 공식 발행은 분리한다.
사용자가 실제로 답한 결정에 불필요한 동일 승인을 다시 요구하지 않는다.

최초 개발 단계이므로 구형 `main`·`cto-inbox`·`decisions`를 위한 사용자 전환 버튼,
이전 기록 메뉴, 마이그레이션은 만들지 않는다. CSAS v0.8 S7 및
AC-CSAS-LEGACY-01~06은 후속 사용자 결정으로 현행 구현 범위에서 제외한다.
실제 데이터가 있다는 추정으로 이전 기능을 만들거나, 없다는 추정으로 데이터를
자동 삭제하지 않는다. 개발·시험 데이터 초기화는 대상 확인과 별도 승인 범위에서만 한다.

## 4. 명세·UI·변경관리

고객 발언, 모델 해석, 제안, 사용자 결정, 위임, 승인 상태를 구분한다.
HTML의 예시 버튼·임시 데이터·데모 동작은 승인된 제품 기능이 아니다.
승인 HTML의 식별자·내용, UI Contract, UI Revision과 요구/기능/화면/상태/동작의
양방향 관계를 추적한다. 제품 HTML 승인 뷰어는 보류한 Core Preview와 다르다.

최초 Baseline 전 변경은 초기 설계 협의다. 이후 추가 요구는 Lead가
Clarification, Correction, Change Request로 구분한다. 상담 수집과 이 분석은
독립적이며 수신만으로 기존 명세나 작업을 바꾸지 않는다.

CR은 old/new 명세·UI·기술·CTO Workstream·Task·일정·상품/견적 영향 후보를
분석하고 실제 사용자 승인 후 새 Revision으로 발행한다. 영향받지 않는 설계·
작업·승인 이력은 보존한다. 영향받은 UI만 재검토 대상으로 만들고, 구 Revision의
결과를 새 Revision 충족으로 자동 인수하지 않는다. CTO는 개정 명세에 맞춰 진행
중 작업의 계속·중단·재작업을 기술적으로 판단한다.

## 5. CTO·Worker·질문과 실행

CTO는 프로젝트별로 필요한 만큼 생성·배정할 수 있다. Graph 노드별 담당 CTO는
한 명이며, 해당 노드의 공동 작업은 CTO가 Worker들에게 나눈다. CTO는 단일 논리
세션과 CTO별 기억을 갖고, Worker/QA는 독립 실행 세션을 갖는다.

고객 상담의 모호성은 Main에서 사용자와 협의한다. CTO의 작업 중 질문은
Intake가 기존 원문·승인 결정에서 해결 가능한지 판단한다. 근거로 해결하면 CTO에
회신하고, 사용자 고유 결정이 필요한 것만 Discussion에 올린다. 키워드 규칙으로
사용자 판단을 대체하지 않는다. 질문에 의존하는 범위만 보류하고 독립 작업은 계속한다.

지속 작업은 목표·최신 명세·진행·다음 조치·실행 참조의 저장/재개로 제공한다.
상주 모델, 커스텀 분산 scheduler, 별도 Job Queue, 무한 CLI 루프를 필수로 만들지 않는다.
기존 Core/SDK/provider의 실제 세션·실행·복구·중단 계약을 우선 재사용한다.
계획 저장/Task Packet 발행/CAO 개발 성공은 제품 Worker가 실행됐다는 증거가 아니다.

### 5.1 CTO 검증 완료와 통합은 별개의 상태

CTO는 담당 Workstream의 개발·내부 통합·독립 QA·필수 검증을 마친 뒤 설계 시각화의
제한된 완료 제출 API로 증거를 낸다. 승인 Spec/UI/Workstream Revision, 실제 소스·
commit/artifact, TestPlan·QA와 필수 결정의 정합성을 백엔드 G4/G6가 검사한 뒤에만
담당 상태를 `NOT_STARTED -> IN_PROGRESS -> VERIFYING -> VERIFIED`로 전환한다.
필수 실패·미검사·UNKNOWN을 합격으로 보지 않는다. CTO 로컬 검증에 아직 존재하지
않는 다른 CTO의 전체 통합/E2E 완료를 요구해 순환 대기를 만들지 않는다.
CTO는 임의 Graph 구조·승인 명세를 편집하지 못하고 해당 상태·증거만 제출한다.

통합 상태는 별도로 `NOT_READY`, `WAITING_DEPENDENCIES`, `READY`, `INTEGRATING`,
`INTEGRATION_HOLD`, `INTEGRATED`, `REVALIDATION_REQUIRED`를 관리한다.
`VERIFIED + INTEGRATION_HOLD`는 가능하다. 단순 보류로 과거 검증 기록을 삭제하지 않는다.
현재 Revision/코드/인터페이스 변경으로 기존 근거의 무효가 확인되면 영향 범위만
재검증 필요로 표시하고 CTO에게 돌려보낸다. 과거 성공 근거와 현재 유효성은 구분한다.

### 5.2 Integration Manager와 이벤트 경계

**2026-11-04 사용자 확정: 독립 Agent와 공용 CLI 풀.** Manager는 Lead와 다른
Agent 식별자로 등록하며 자체 역할 지침·권한·프로젝트 세션·작업 기록을 갖는다.
필요한 Agent 프로필은 시스템 기본값으로 생성하고 이후 개별 설정을 바꿀 수 있다.
별도 CLI 인증 계정 추가 등록을 필수로 하지 않는다. 기존 CLI 공용 풀에서 실행에
적격한 인증 프로필을 배정받으며, Agent 정체성과 인증 계정의 정체성을 혼동하지 않는다.
공급자·모델 등 기본 실행 설정은 Lead 설정을 초기값으로 재사용할 수 있지만
Lead Agent 자체나 그 권한·세션·기록을 공유하는 것은 아니다. 기존 실행 권한과
프로필 적격성 검사는 유지하며 이 결정이 한도 우회나 인증파일 복사를 허용하지 않는다.
자동 기본 프로필 생성에 필요한 Core/SDK 계약은 실제로 확인하고, 미지원이면 필요한
선행 기능으로 기록한다. 생성·실행이 아직 없는데 사용 가능한 것처럼 표시하지 않는다.

백엔드의 검증·상태 저장이 성공한 `WorkstreamVerified` 이벤트만 Manager를 깨운다.
프로젝트/Workstream/체크포인트/검증 Revision/기준선/UI/소스·산출물/QA/event ID·시각을
원본 기록으로 연결한다. Gate 성공, 상태 저장, 지속 이벤트 결속은 실제 저장소의
원자적 경계로 보장해야 하며 UI 표시나 LLM 출력으로 이벤트를 만들지 않는다.
기존 Core·SDK·Graph·Revision·CSAS·이벤트 기능을 먼저 재사용한다. 새 분산 큐나
상주 scheduler를 요구하는 것은 아니다. 기존 경계의 지원 여부는 실제로 확인한다.

오프라인/재시작에도 미처리 이벤트를 복구하고 중복·재전송은 같은 통합을 중복 실행하지
않는다. 프로젝트/후보 브랜치 단위 lock/lease 또는 동등한 실제 소유권으로 동시 통합을
조정한다. 시작 및 commit/merge 직전에 최신 승인 Revision·Gate·의존성·권한을 재확인한다.
통합은 격리된 후보 브랜치/작업공간에서 수행하고 필수 CI/QA 전에 기준 브랜치에
직접 반영하지 않는다. 정상 의존 대기는 `WAITING_DEPENDENCIES`로 보존하고 자원을
계속 점유하거나 Main/Integration Review를 반복 호출하지 않는다. 무관한 준비 영역은
다른 CTO의 전체 완료를 기다리지 않고 통합한다.

Manager는 승인 명세·Graph·Task·QA 원본을 필요한 범위에서 조회하고 통합을 실행한다.
고객 대화 전체의 무제한 조회·사용자 결정·공식 설계 개정 권한은 갖지 않는다.
Manager와 Integration Review 로그는 원본 ID를 유지해 분리하며 대화를 복제하지 않는다.

### 5.3 통합 이슈 라우팅과 최종 반환

- 일반 CTO `VERIFIED` 이벤트는 Manager로 가며 Lead Main을 매번 깨우지 않는다.
- merge/build/test 등 승인 계약 안의 기술 오류는 담당 CTO에게 직접 반환한다.
- 설계·승인 요구와 구현의 상충, 교차 CTO 계약·결정권 문제는 해당 통합만 보류하고
  Integration Review로 보낸다. Review는 기존 설계·원문 근거로 조정하고 담당 CTO에게
  수정 지시를 전달한다. 공식 명세 개정은 기존 Main 발행 경계를 따른다.
- 사용자 고유 결정만 기존 Question Discussion으로 보내고 필요한 CR/Revision에 연결한다.
  같은 문제를 Intake/Review/Discussion에 중복 게시하지 않는다.
- 전체 요구 Workstream 통합과 E2E·회귀·G6 검증이 끝나면 Manager가 Final Integration
  Packet을 Main에 전달한다. Main은 전체 승인 설계·QA·산출물 완비와 G7을 최종 점검한다.

Final Integration Packet은 프로젝트·승인 Baseline/UI/검증 Revision, 포함 Workstream/Task·
commit/artifact/PR, 통합 후보·빌드 해시·CI, 기능/인터페이스/UI 추적 관계, E2E/회귀·QA,
미검증 범위·해결 이슈·제한, 납품 후보/문서 참조와 G6 상태·남은 G7 점검을 포함한다.
필수 검증이 미완료면 최종 통과로 전달하지 않는다. 패킷은 새로운 설계 원본이 아니다.
설계 시각화와 문서센터는 검증 완료/통합 보류/재검증·담당·blocker·다음 조치·증거를
별도 축으로 보여 주고, 통합 이슈/결정/시도/재개/패킷을 기존 정식 기록에서 조회한다.

### 5.4 사용자 전용 최종 검토·승인

2026-11-05 사용자 결정에 따라 기존 Integration Review는 내부 이벤트 검토를 유지하면서
좌측 Lead 영역의 `최종 검토·승인` 페이지를 제공한다. Manager는 별도 Agent이고 Review용
Agent나 일곱 번째 Lead 세션을 추가하지 않는다. 설계·계약의 사용자 고유 결정은 계속
Question Discussion으로 라우팅하며 납품 버전 승인을 그 질문 기록과 중복 확정하지 않는다.

Manager의 실제 Final Integration Packet 이후 Main이 현재 승인 설계·계약·QA와 G7을
대조한 적격 후보만 불변 스냅샷 참조로 승인 요청을 발행한다. 페이지는 요청 목록/빈 상태,
납품 파일명·상대 경로·크기·버전·해시, 설치·사용법·지원 환경·의존성, 제한·변경 내역과
CI/E2E/QA/G6/G7·명세/문서 Revision 및 원본 증거를 표시한다. 실제 문서센터의
Artifact/Revision을 참조·미리보기하고 복제된 정본이나 독립 승인 DB를 만들지 않는다.

기존 Core/SDK의 현재 Workspace 접근·승인 권한을 만족하는 실제 사용자만 `승인`,
`수정 요청`, `보류`를 제출한다. Agent/system/Lead/Manager가 사용자 대신 확정할 수 없다.
별도 Core Project ACL이나 새 사용자 역할 체계를 이 결정으로 발명하지 않는다.
서버 진입점은 현재 사용자·Workspace·요청/후보/Packet/기준선/UI/파일·문서 해시와
필수 QA/G6/G7을 확인한다. 실패·누락·UNKNOWN·stale이면 UI뿐 아니라 직접 API도
확정을 거부한다. 기존 Revision/CAS·감사 경로의 실제 원자적 범위를 확인하고, 서로 다른
저널의 관측상 재확인만으로 전역 원자성을 주장하지 않는다. 필요한 기술 선행 기능은
명시하고 미구현 상태를 사용자 승인이나 caller PASS로 우회하지 않는다.

확정 성공은 승인자·시각·참조 Revision·파일/문서 해시와 Workspace의 현재 공식 패키지
버전을 연결하며 중복 클릭·응답 유실 재시도·재시작·경합에도 중복 발행하지 않는다.
수정 요청/보류의 사유와 감사 이력을 보존하고 Main/Manager/해당 CTO로 환류한다.
산출물·관련 문서·기준선 변경 시 옛 승인을 삭제하지 않고 새 후보를 재승인 대상으로
만든다. 납품 구성 확정, QA 합격, 고객 전달, 계약·결제, 외부 배포는 별개의 상태다.

추가 인수 기준 AC-APP-01~14는 기존 추적표에 통합한다. 예시 상태명·필드명을 정식
스키마나 구현 완료로 간주하지 않으며, 기존 납품/Revision 저장 기능의 확장을 우선한다.

### 5.5 역할 정책과 범용 기술 권한·Host 사전 위임

2026-11-05 사용자 확정에 따라 Builder는 업무 역할과 권한 템플릿을 정의하고, Core는
Agent/CLI/Runner/파일/프로세스/Secret/Node/Workspace·Artifact/네트워크의 범용 기술 권한을
발급·검증·관리·철회한다. Core에 Builder 전용 역할이나 Manager 예외 권한을 하드코딩하지 않는다.
[추가안](01_Design/SPS_Builder_Generic_Permissions_And_Host_Delegation_Addendum_2026-11-05.md)의
역할별 책임과 기본 권한·작업 임시 권한·Host 사전 위임·사용자 전용 승인을 모두 적용한다.

Host 관리자가 승인한 Host/Workspace/Plugin/역할/Node/Runner 범위에서는 독립 Manager가
Agent별 수동 등록·새 CLI 계정 없이 실행한다. 실제 적격 인증 풀 배정은 Core가 맡으며
인증정보를 노출하지 않는다. 위임은 Agent 실행만 허용하고 파일/Git/CI/일반 Node 관리나
납품 승인 권한을 함께 주지 않는다. 승인 CTO 완료 이벤트·통합 계약과 현재 별도 권한을 검증한다.
만료·철회·동시 실행 한도·이력을 관리하고, 신규 차단과 실제 진행 실행 취소/종료를 구분한다.

권한은 실제 Workspace/Plugin/주체/대상 자원/작업 범위/기간에 결속한다. 정상 승인 범위의
반복 요청은 없애되 범위 확대·다른 Workspace·보호 자원 변경·사용자 전용 결정은 우회할 수 없다.
QA Worker의 명시된 테스트/설정 수정은 허용하되 검증 독립성·실제 대상 결속·결과 무조작을 유지한다.
Main 공식 발행 및 사용자 제품·계약·가격·최종 납품 결정 경계는 그대로 유지한다.

기존 실제 Core/SDK 계약을 우선 재사용하고 필요한 중립 확장과 호환성을 별도로 보고한다.
설계 승인을 runtime Host 관리자 Grant나 구현 완료로 바꾸지 않는다. API/Workspace 검사만으로
CLI의 OS 파일·프로세스·Secret 격리가 보장되지 않으며 실제 OS 통제/샌드박스 검증이 필요하다.
기존 216개 원문 AC는 유지하고 추가 정책은 추적표의 파생 검증 overlay로 관리한다.

### 5.6 실행·인계·QA·복구와 실제 속도

2026-11-05 사용자 요청에 따라 [실행 계약 보강](01_Design/SPS_Builder_Execution_Handoff_And_Recovery_Addendum_2026-11-05.md)을 적용한다.
실제 Core 위임·적격 풀·보호 TestPlan·실행 증거·Commit 인계가 없으면 선행 의존성으로 분리한다.
Lead→CTO→Worker→QA→Manager의 기존 Task Packet에 Task/Workstream/승인 Revision/Commit/
Artifact/TestPlan·QA·환경·멱등 인계 참조를 결속하고 생산자 완료와 소비자 인수를 구분한다.
QA는 불변의 실제 검사 Commit에 연결하며 Graph/trace로 영향받은 범위만 재검증하고 무관한
검증을 보존한다. 개발 snapshot 검사를 최종 Commit QA로 승격하지 않는다.

권위 저장 완료 이벤트만 Manager를 자동 실행시키며 정상 의존 대기와 기술 오류를 분리한다.
모든 실행에 총 재시도·시간 한계, 실패 분류, 다음 조건·관측·정체 한계·복구 담당과 중복 방지가
필요하다. timeout만으로 재실행하거나 종료 불확실 슬롯을 재사용하지 않는다. 정상 승인 범위는
반복 사용자 요청 없이 진행하고, 속도는 실제 완료/대기/재작업 시간과 수동 개입으로 측정한다.

최종 인수는 실제 CTO 2개 이상의 병렬 Workstream→Worker 제출→정확한 Commit 독립 QA→
저장 이벤트 기반 Manager 자동 통합과 실패·철회·소스 변경·재시작·지연 복구를 포함한다.
설계 반영, fixture 통과, 실제 앱·AI/보호 실행 검증은 분리한다. 새 Agent/중복 시스템은 추가하지 않는다.
기존 216개 원문 AC를 보존하고 POLICY-EXEC-01~16은 별도 NOT_RUN overlay로 추적한다.

공용 풀 전환은 실행 계약 보강 §9 및 [시스템 완료·선택적 Wake 확정 설계](01_Design/SPS_Builder_CLI_Pool_Completion_And_Selective_Wake_Addendum_2026-11-05.md)를 따른다. 모든 역할이 하나의 활성 CLI 계정을
공유하고 세션 등록·로컬 Session ID 보존과 실행 점유를 분리한다. PREPARE/RESUME/WAKE는
독립 동작이며 복원만으로 모델을 호출하지 않는다. 무호출 복원이 미지원/미검증이면 PREPARE까지만 한다.
시스템 실행 이벤트로 RUNNING/DONE/INTERRUPTED/IDLE을 관리하고 Agent의 DONE 보고를 강제하지 않는다.
DONE은 마지막 AI 실행의 정상 종료이며 Task/CTO VERIFIED/QA/통합 완료가 아니다.
전환 직전 RUNNING이고 전환/인증으로 실제 중단됐으며 정상 완료 없이 미완료 작업·안전한 종료가
확인된 세션만 최종 상태 재조회와 세대/Run/Event/requestId/CAS 검증 뒤 continue로 자동 Wake한다.
사용자·승인·의존성 대기는 해소 이벤트, 중단 세션은 명시 재개 요청으로 Wake한다. 완료·보관은
깨우지 않는다. 계정 간 서버 소유권을 로컬 복원 조건으로 삼지 않되 현재 권한·Revision과
프로세스 종료·중복 방지는 검증한다. 지연/누락 완료와 완료 직후 전환은 DONE 우선이며 불확실하면
자동 Wake하지 않는다. 별도의 공급자 정책 확인·승인에 따른 활성화 조건은 추가하지 않는다.
실제 A→B 인증 모델 요청은 로컬 복원과 별도 인수하며 미검증이다. 9개 실제 CLI 인수와 제품 연결은
NOT_RUN/미검증이며, 사용자 후속 지시에 따라 이 추가 기능의 구현은 보류한다.

## 6. CSAS와 G0~G7

CSAS는 별도 상위 AI가 아니라 명세·근거·결정권·범위·Revision·증거·게이트의
공통 체계다. CTO의 기술 설계와 테스트 책임을 대체하지 않는다.

| Gate | 경계 | 현재 의미 |
| --- | --- | --- |
| G0 | 고객 요구·상품·견적 | 계약 범위·추가 비용·권리·상품 정합성; 자동 결제 확정 금지 |
| G1 | 상담에서 명세 | 출처·기능·상태·예외·미결정·AC와 UI 관련 계약 식별 |
| G2 | 설계/UI 후 기술 선정 | 재사용·Capability·환경·라이선스·전체 운영비용 확인 |
| G3 | Lead에서 CTO | 커버리지·의존성·인터페이스·승인 UI·소유권·승인 Revision |
| G4 | CTO에서 Worker/실행 | Task·허용 부작용·결정권·테스트·실행 시점 Revision |
| G5 | 설계 변경 | 명세/UI/Graph 양방향 영향·ACK·stale·부분 재검토 |
| G6 | 구현에서 통합 | 독립 QA·명세·UI·테스트·구현 증거와 양방향 추적 |
| G7 | 최종 산출물 준비 | 계약상 실행물·설치/사용 자료·테스트·제한; 고객 자동 전달 제외 |

이 의미는 CSAS v0.8 F절의 현행 결정이다. 옛 G1~G6 제안서에 `초안`이라고
적혀 있다는 이유로 G0~G7 전체를 미정으로 되돌리지 않는다. 구체 스키마·조회
어댑터·저장·테스트 방법은 실제 계약을 확인해 CTO가 설계하고 교차 계약은 Lead가 조정한다.

검사 구조, 기록 저장, 사용자 승인, 실행 허가, 테스트 합격, 고객 인수는 서로 다르다.
모델/클라이언트가 준 `PASS`·`verified` 값은 권한 증거가 아니다. 실제 저장소의
현재 source/scope/Revision/권한과 독립 QA 근거를 확인한다. 확인 수단이 없거나
검사가 실패·불완전하면 UNKNOWN/INCONCLUSIVE로 기록하고 해당 허가를 내주지 않는다.
실제 Task 발행·Worker 실행·결과 인수 진입점에서 재검증해야 하며 순수 함수 시험만으로
그 진입점의 차단이 구현됐다고 주장하지 않는다.

## 7. D3 지속형 명세 검증과 G5

D3 전체 흐름은 원문/승인 명세 -> 요구 추출 -> Domain Pack 선택 -> Coverage ->
상태/이벤트/예외 -> 필요시 조건·반례 검사 -> Gap -> Intake/해결 -> 승인 Revision ->
실제 Task 발행/인수 게이트다. 구조 검사 하나로 전체를 완료 처리하지 않는다.

팩은 공통·세부 상품·기능 도메인·위험/환경을 조합하고 규칙·버전·적용 조건·중복을
추적한다. 검토하지 않은 범위는 문제없음으로 표시하지 않는다. 불가능한 상태 조합의
제외 근거, 검사기/모델 범위, 오류·시간 초과·부족한 입력을 보존한다.
Gap은 원문·requirement/UI/contract·Task/Workstream·결정권자·검출 방법·중복 지문·
해결 근거를 연결한다. 특정 외부 solver나 명세 도구의 전면 도입은 자동 승인하지 않는다.

G5는 실제 old/new Revision과 승인 UI를 기준으로 영향 후보를 산출한다.
일곱 영향 차원의 누락·범위 밖·미확인은 구분하고, 후보 계산이 승인이나 실제 실행을
대신하지 않는다. 코드/타입/Git 의존성 도구는 보조 수단이며 요구·UI 관계를 대체하지 않는다.

### 7.1 검증 근거 발행과 확정된 승인 경로

현재 승인 명세의 요구사항 ID·설명·AC ID만으로 요구사항별 상담 원문 연결이나
적용할 Domain Pack·사실 모델의 확정 상태를 추론하지 않는다. 원문 내용의 동일성,
AI가 해석한 요구사항 관계, 사용자 설계 승인, 검사 실행·합격은 별개다.
정규화한 JSON이나 저널 해시는 원문 내용·의미 관계·승인의 대체 증거가 아니다.

Builder가 기존 원문 저장소와 Workspace/project 범위의 저널을 재사용해 출처 관계와
버전별 검증 근거를 제공한다. Core에 업무 Task나 별도 승인 모델을 추가하지 않는다.
구체적인 스키마·저장 형태·조회 인터페이스·TestPlan은 담당 CTO가 설계하고,
공유 발행·실행 진입점에는 한 명의 구현 소유자만 둔다. 임시 CAO 개발 QA 기록은
Builder 제품의 실제 독립 QA 실행 증거로 가져오지 않는다.

**사용자 확정:** AI가 요구사항-원문 연결과 적용할 버전별 검증 규칙 묶음을 초안으로
만들고 사용자가 설계 검토 화면에서 확인한 뒤, 그 특정 버전을 Design Baseline
승인에 함께 포함한다. 별도의 중복 승인 절차를 기본으로 추가하지 않는다.
이는 검사기/QA 결과의 자동 합격이나 향후 문서·규칙 전체의 포괄 승인이 아니다.

승인 대상 원문·연결·규칙·Revision과 사용자 승인 근거를 고정하고 Main의 공식
발행 경로에서 재검증한다. 초안 저장·버전 격리·현재 기록 조회를 재사용하되,
승인 이벤트와 실제 진입점 연결이 구현·검증되기 전에는 초안을 승인으로 취급하지 않는다.
기존 기준선과 승인 이력을 보존한다.
누락되거나 미승인인 연결·규칙·QA는 UNKNOWN으로 남지만, 이 임시 상태나 fixture
어댑터만으로 전체 D3·G0~G7 또는 실제 사용자 흐름을 완료 처리하지 않는다.

### 7.2 최초 기준선 이전의 검토와 공동 승인

첫 기준선도 §7.1의 같은 사용자 검토·공동 승인 흐름을 제공한다. 기존 승인 기준선이
없다는 이유로 검토를 생략하거나, 임시 승인본을 먼저 만들어 순환 의존을 숨기지 않는다.
이는 별도 승인 정책 추가가 아니라 확정된 초기 설계 -> 검토 -> 최초 Baseline 흐름의
구현 계약을 명확히 하는 것이다.

조사한 기존 초기 초안 출처는 `src/design-draft-store.ts`의 `createDesignDraftStore`와
`src/domain/design-drafts.ts`의 DesignDraft다. 기존 `publishDesignBaseline`도
`sourceDraftRevisionId`를 읽는다. 이 출처를 우선 재사용하며, 기준선에만 묶인 Assurance
draft reader를 최초 초안용 API라고 주장하지 않는다. 부족한 초기 검토 묶음과 UI/action
연결은 Builder가 추가해야 할 구현이며 아직 존재하는 승인 API로 보고하지 않는다.

최초 검토 묶음은 실제 Workspace/project, 현재 초기 설계 초안의 불변 버전·내용,
해당 초안의 요구-원문 연결·적용 규칙 팩의 특정 버전에 묶인다. 이전 승인 기준선의
부재는 명시적인 최초 상태로 표현하며 가짜 ID·빈 문자열·합성 승인 근거로 대체하지 않는다.
후속 검토는 같은 원칙에 실제 이전 기준선/변경관리 관계를 추가한다. 구체 스키마·키·
어댑터는 CTO가 정하되 원본 저장소·Revision 저널을 재사용하고 별도 문서 DB를 만들지 않는다.

권한 있는 실제 사용자의 검토/승인 action과 Main의 공식 발행은 분리한다. action의
사용자·scope는 인증된 Host 컨텍스트에서 얻으며 AI가 보낸 사용자 ID·승인 문장·해시만으로
승인 사실을 만들지 않는다. 최초 기준선에도 검토한 초안·원문 관계·규칙 버전과 승인
근거를 결속한다. 이는 내부 설계 승인이지 고객 법적 서명·QA 통과·코드 실행 허가는 아니다.

공식 기준선과 필요한 검토 버전 참조는 원자적인 권위 발행 경로로 함께 확정한다.
실제 CAS/권한·초안/승인 버전 검증 없이 get/set이나 여러 저널 갱신을 원자적이라고
부르지 않는다. 실패한 사전 저장은 미발행 기록으로 남기고, stale/불완전/취소/권한 회수는
현재 기준선을 바꾸지 않는다. 사용자가 확인한 버전과 발행 시 검증 대상이 달라지면
자동 승인·자동 재시도 대신 충돌을 돌려준다. 승인본과 과거 검토 근거는 보존한다.

## 8. 프로젝트 문서센터와 최신성

[문서센터·최신성 보완 v1.1](01_Design/SPS_Builder_Project_Document_Center_and_Freshness_Addendum_v1.1_2026-11-04.md)을
현행 설계에 통합한다. 원문은 보존하며 아래 내용은 제품 요구와 구현 경계를 정리한다.
첨부 내 CAO Lead 전달 문구는 개발 업무 자료이며 별도 AI Lead 생성 지시가 아니다.

### 8.1 하나의 문서 열람 화면

프로젝트 좌측에 `문서`를 두고 중앙 작업영역에 독립적인 문서센터를 제공한다.
기존 `documents`/설계 문서 화면의 진입점과 읽기 기능을 확장하며 중복 메뉴를 만들지 않는다.
문서센터 자체는 새 AI 세션이나 승인 권한 계층이 아니다. Lead의 여섯 논리 세션과
별도 Integration Manager, CTO/Worker, 전역 미결정사항, HTML 승인 뷰어를 대체하지 않는다.

문서 분류/저장 필터, 목록, 미리보기/상세를 제공한다. 이는 기능 구분이며 고정 3열을
좁은 viewport에 강제하지 않는다. 상세 정보는 센터 내부 패널/탭에 두어 전역 질문
영역과 충돌하지 않게 한다. 테마와 배치는 UI v9 및 실제 Shell 계약을 따른다.

기본 분류는 상담 자료, 설계 문서, UI 설계, 검증 기준, 기술 조사, 개발 작업,
변경 이력, 테스트·QA, 납품·사용법의 아홉 가지다. 논리 분류이지 아홉 개의 별도
파일 저장소를 요구하지 않는다. 제목/본문 검색, 분류/유형/승인/최신성 필터,
수정 시각 양방향·제목·유형·Revision 정렬, Requirement/CR/Workstream 연관 필터,
승인됨/검토 필요/초안 보기를 제공한다. 수정 시각을 최신성 증거로 사용하지 않는다.

v1.1 §3·§5.2의 분류는 기존 정식 데이터에 대한 논리적 매핑이다. 기본 분류 목록이나
분류별 조회 연결에 별도의 사용자 승인·서명·승인 Registry를 추가하는 것은 선행조건이
아니다. 서버가 관리하는 실제 유형/분류 매핑과 해당 버전을 확인해 사용하며, AI나
클라이언트가 보낸 분류·완전성 선언만 믿지 않는다. 분류 매핑 확인은 실제 Host의
Workspace/project 조회 권한, 문서·본문·출처·Revision 및 의존관계 검증을 대체하지 않는다.
목록 페이지의 수신이나 분류 확인만으로 전체 문서 열거·의존 추적의 완전성을 주장하지 않는다.

목록은 제목·유형·Revision·승인·최신성을 표시한다. 상세에서는 작성 주체·시각,
Workspace/project·문서 ID·원본/해시·참조 기준선과 관련 ID·승인 근거·최신성 사유,
연결 문서와 변경 이력을 확인한다. 상담 -> 요구 -> 명세/UI -> 검증 -> 작업 -> QA ->
산출물 연결을 원본 ID로 따라가며 관련 문서 상태도 확인할 수 있어야 한다.

### 8.2 읽기 쉬운 통합 기준선

사용자는 하나의 통합 설계 기준선 문서를 중심으로 프로젝트를 읽는다. 구성은
개요/상품 범위, 요구/근거, 기능·데이터·권한, UI/승인 시안, 검증 요약, 기술/재사용,
CTO Workstream/의존성, 결정/미결정, 변경/현재 Baseline의 아홉 항목이다.
Requirement·Validation·UI Contract·Task·QA 등 구조화 데이터는 기존 정식 저장소의
독립 ID를 유지하고 통합 문서에서 상세로 연결한다. 원문 대화나 같은 사실의 수동
복제본을 여러 문서에서 독립 수정하는 구조를 만들지 않는다.

정식 데이터/승인 Revision에서 생성하는 읽기 View와 승인 시점의 불변 스냅샷을
구분한다. 승인된 문서 본문은 이후 템플릿이나 데이터 변경으로 다시 렌더링해 바꾸지
않는다. 현재 최신성 정보는 과거 본문·승인 사실과 별도로 계산해 표시할 수 있다.
Markdown 열람/내보내기는 포함하고 PDF는 후속 검토 대상이다. 내보낸 파일에는
문서 ID·참조 Revision/원본 링크·생성 시각을 넣어 특정 시점 스냅샷임을 표시한다.

### 8.3 이벤트·승인·최신성

승인 상태와 최신성은 별개의 축이다. v1.1의 상태명은 의미를 설명하는 예시이며
기존 스키마를 무조건 교체하는 고정 enum은 아니다. 승인된 문서가 검토 필요가 되어도
과거 승인자·시각·근거를 삭제하거나 소급 취소하지 않는다.

| 이벤트 | 허용되는 갱신과 보존 경계 |
| --- | --- |
| 상담 수신 | 원문·중복 제거·순서·수집 상태만; AI 분석·전체 문서 재작성 금지 |
| 명시적 상담 분석 | 고정한 원문 범위로 분석·요구/출처 초안 생성 |
| 설계 초안 수정 | 관련 초안/미리보기 갱신; 승인본 대체 금지 |
| Baseline 승인 | 검토한 출처 연결·규칙 버전을 포함한 승인 스냅샷 고정 |
| UI/검증 기준 승인 | 해당 승인 버전과 연결된 자료 갱신; 승인 범위 확대 금지 |
| CR 접수 | 변경 제안·영향 초안; 현재 승인 기준선 유지 |
| CR 승인 | 새 명세 Revision과 영향 문서 초안/Revision; 기존 이력 보존 |
| Workstream/Task 변경 | 해당 작업 문서·연결 요약 갱신; 승인 명세 본문 불변 |
| 테스트/QA 완료 | 실제 결과·증거·인수 상태 갱신; 설계 기준선 수정 금지 |

정식 Revision과 추적 관계로 영향받는 문서만 검토 필요/오래됨 상태 및 사유를 기록하고
새 초안을 만든다. 무관함이 확인된 문서만 현재 상태를 유지한다. 연결·권한·원본이나
판정 근거가 부족하면 UNKNOWN/검토 필요로 표시하며 AI가 임의로 CURRENT를 선언하지 않는다.
새 수신 메시지를 기존 분석 snapshot에 섞거나 수신 자체를 승인 설계의 변경으로 보지 않는다.
사용자가 승인하지 않은 초안은 공식 기준선을 대체하지 않는다.

이전/현재 Revision, 요구·검증 규칙의 추가/삭제/변경·제외 사유, UI/HTML 변경,
Workstream/Task 영향, 승인 이력, QA 증거의 현재 유효성을 비교한다.
오래된 이벤트·중복 이벤트·비동기 결과·재시작 시에도 최신 승인 포인터를 되돌리지
않아야 한다. 전체 문서의 주기적 AI 재작성으로 최신성을 대신하지 않는다.

Main의 공식 명세 발행, 사용자 승인, 각 논리 세션/CTO/Worker/QA의 담당 산출물
작성 경계를 유지한다. 열람 가능성이 수정 권한은 아니다. 목록·검색·본문·연결·비교·
내보내기도 같은 Workspace/project/현재 권한 경계를 지킨다.

### 8.4 실제 재사용 계약과 구현 순서

2026-11-04 조사한 개발 소스 기준으로 Builder에 `documents` 화면과 문서 목록/
미리보기 기초는 있으나 프로젝트 분류 연결·위 최신성 계약 전체의 완료 증거는 없다.
Core/SDK에는 scope가 있는 state, 선택적인 company CAS, 인증된 UI data/action,
Artifact publish/list가 있다. Project 문서 의미·승인·업무 Revision·의존 추적은 Builder 소유다.

SDK c699의 CAS는 구 Host에서 없을 수 있고 company 범위·직렬화 요청 262,144-byte
등 제한이 있다. get/set 조합을 CAS처럼 흉내 내지 않는다. 별도 runtime facade의
Artifact는 subject/run 참조와 JSON을 담지만 프로젝트 승인/Revision 엔진이 아니다.
관측 Core의 Artifact summary/data는 각각 100,000-character 제한이며 list는 최대
200개다. 이를 전체 문서 검색·대용량 원문·모든 기록의 완전한 목록으로 가정하지 않는다.
실제 설치 Host의 facade/capability/권한·viewport 지원은 통합 시 다시 확인한다.

기존 원문·Revision·CAS 저널·Artifact를 재사용하고 중복 문서 DB·Core 업무 모델을
신설하지 않는다. 정확한 인덱스/렌더러/저장 분할·페이지 전략·이벤트 처리·테스트는
CTO가 정한다. Markdown/HTML은 안전하게 표시하며 콘텐츠 실행이나 경로/권한 우회를
새로 허용하지 않는다. 비공개 Core 구현은 공개 레포에 복사하지 않는다.

의존 순서는 (1) 기존 저장·권한·Revision 조사와 최소 문서 조회/최신성 계약,
(2) 독립 데이터/상태 계산과 센터 읽기 UI, (3) 한 소유자의 승인/변경 이벤트 연결,
(4) 독립 QA와 실제 앱의 검색·비교·내보내기·격리·승인 보존 검증이다.
새 Task/path grant가 발급되기 전에는 계획만으로 기존 작업 범위를 확대하지 않는다.
AC-DOC-01~16은 기존 단일 추적표에 원문·출처·해시와 함께 편입하고 처음에는 NOT_RUN으로 둔다.

2026-11-04 다음 개발 단계에서는 문서 조회/승인본 연결(CTO-A), 최신성 계산(CTO-B),
실제 Worker 실행(CTO-A), 단일 공유 UI/공식 승인 연결(CTO-A), 납품 근거(CTO-B)의
다섯 구현·독립 QA 쌍을 실제 분리 경로로 배정했다. 검토된 공통 소스는
`53ea1d7d9ecfa54bec26358be9a7b940958f58af`이며
`codex/builder-cp3-common-source-20261104` 브랜치로 보존했다. 이 공통 소스는 새 단계의
입력이지 이후 Worker WIP나 새 기능의 완료 증거가 아니다. 문서센터 AC 전체는
계속 NOT_RUN이며 현재 소스·독립 QA·실제 앱 증거를 연결한 뒤에만 인수 상태를 바꾼다.

## 9. UI·상품·납품 및 보류 범위

UI v9 구조와 승인 UI 적용 기준을 유지한다. 검정·중립 회색과 폰트·패널 기준은
Builder 플러그인 내부에만 적용하며 Core 전역 UI를 바꾸지 않는다. 샘플 대화·AI·
Runner·완료율을 실제 상태처럼 채우지 않는다. 미연결 기능은 명확히 표시한다.

상품은 기존 S/M/L/XL 및 세부 카탈로그 ID·버전을 참조하고 임의 상품/가격을 발명하지
않는다. 초기 추천과 최종 범위/견적은 구분한다. FAST/ASSEMBLY/CUSTOM·독립 앱·
웹·API·자동화·Agent·SPS Plugin 같은 기존 v15 목표를 현재 기초 모듈 범위로 축소하지 않는다.

G7은 계약에 맞는 프로그램·필요한 설치/실행/사용 안내·테스트/QA·알려진 제한을
준비하는 단계다. 대외 전달·고객 서명·실제 결제·배포를 자동 수행하지 않는다.
전체 통합과 Main 최종 점검 이후 Main이 실제 산출물/검증 결과에 결속된 납품 목록·
설치·사용법·알려진 제한 초안을 작성한다. 인증된 사용자가 그 정확한 버전을 확인·
확정하고 변경 전 이력을 보존한다. 이미 확정한 요구·설계를 다시 승인받지 않는다.
초안 저장은 확정이 아니며 확인되지 않은 가격·카탈로그·고객 계약을 발명하지 않는다.
납품 문서 확정·QA 합격·외부 배포 승인·실제 고객 전달은 서로 다른 기록이다.

Marketplace, 자체 Native 대체 연결, Core Preview는 보류한다. 제품 HTML 승인 뷰어,
기존 Tailscale 이용, 실제 지원되는 provider Worker 실행과 혼동하지 않는다.
과거 AC의 보류 부분은 삭제/합격으로 바꾸지 않고 별도 표시한다.

## 10. 현재 검증·버전과 완료 판정
