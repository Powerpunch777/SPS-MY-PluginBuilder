### 2026-11-07 Task 인수·보호 QA 후속 연결

- `f0aa9b0`과 `68ab18c`는 Worker의 정확한 제출 Commit/Tree를 현재 Task에서 찾고,
  해당 CTO가 받은 사실을 불변 인수 기록으로 남긴다. 인수는 현재 branch tip이나 QA 합격이 아니다.
- `d956754`·`ce65860`·`c737c09`는 현재 독립 QA Worker의 실제 dispatch Run, 개발 Task 의존 핀,
  인수 기록, Host Source/branch proof와 승인된 테스트 계획을 결합한다. 요청 ID와 subject는
  이 원본 핀에서 결정하며 임의 대체하지 않는다. 과거 Task-to-Run 참조는 기존 Revision
  journal에 보존하고, Core가 실행 상태의 원본이다. QA 대화가 끝나도 CTO의 읽기 전용
  조회는 가능하며 새 AI 실행을 만들지 않는다. 변경된 Task/소스의 결과는 이력으로 남긴다.
- 후보 SDK/Host의 실제 Worker subprocess와 임시 DB/Git에서 메타데이터만으로 실행 요청,
  같은 요청의 단일 기록, 철회·다른 Workspace·소스 핀 불일치 거부를 확인했다. 별도의 격리
  시험은 서명된 요청과 실제 보호 실행의 완료·종료 확인까지 연결했다. 이 두 증거를 합쳐
  실제 Builder의 AI QA 또는 두 CTO 종단 간 인수가 완료됐다고 주장하지 않는다.
- 보호 실행의 `succeeded`는 기술 실행 결과다. 등록된 QA 보고 경로는 개발 Task의 인수 조건,
  QA Task의 인수 조건과 테스트 계획 기준을 모두 평가하고, 정확한 Core 완료 receipt와
  독립 QA 작성자를 고정한다. 실패·미검사 항목은 합격으로 바꾸지 않는다. 현재 이 보고
  경로의 독립 fixture QA는 작성 권한·정확한 기준·Task/등록 변경 중 CAS 거부를 확인했다.
  실제 Core 영수증을 받는 통합 QA와 실제 AI QA 수행은 별도 검증 대상이다.
- `f587dcb`는 같은 실행 이력에서 QA 작성 판정, Core 영수증 일치 여부와 작성자 Run의

### 2026-11-09 연결 Task 재발행과 G5 비교

- 기존 `builder.publish-task-packet`의 선택 `additionalPackets`로 같은 Workstream의
  연결된 개발·QA Task를 한 보드 CAS에 발행한다. 모든 packet은 명시한 다음 Revision이고,
  의존성 핀은 입력 순서와 무관하게 최종 보드의 정확한 Revision/digest를 사용한다.
  단건 요청, 기존 이력, 권한 검사와 결과 불확실 시 조회 규칙은 유지한다.
  섞인 Workstream Revision, 권한 밖 Task, 순환·중복·잘못된 companion은 보드에 반영하지 않는다.
- G5는 기존 정확한 old/new 발행 쌍에서 `recordedTaskInputs`를 읽기 전용으로 비교한다.
  두 방향 Graph 연결, 승인 요구사항/AC·원문 핀, Task 의존성, UI와 기술·검증 기준을 대조한다.
  비교의 동일 판정은 기록된 입력 범위만 뜻한다. 제품 전체 영향, 과거 QA 재사용,
  새 G6/VERIFIED 또는 이전 Run의 권한을 승인하지 않는다. 검증되지 않은 외부 Workstream
  의존성, 승인·모델 누락이나 오래된 Task 핀은 `unknown`이다.
- 실제 Builder 등록 도구로 승인과 Task 발행을 재현했다. 단건 재발행의 최초 실패를 보존했고,
  동시 발행·기존 이력·동일 요청 조회 및 불완전 묶음 거부를 확인했다. 정확한 변경 범위 밖
  승인 뒤에도 이전 Run의 쓰기는 차단되며, 새 권한으로 재등록한 쓰기만 가능했다.
  `445f07d`의 실행 관련 394개 파일을 물리 QA 사본과 대조해 모두 일치했다. 후보 SDK
  `8a389d8` 사본의 전체 회귀 1,456개와 빌드, 고정 SDK `c69915a` 사본의 독립 5개와
  타입 검사가 통과했다. 아래 역사 QA reader의 별도 검사 수를 전체에 더하지 않는다.
  Core/Run 응답은 fixture다. 공식 Goal 실행·실제 QA·OS 및 두 CTO 전체 통합 인수와 구분한다.
- 별도 서버 전용 QA reader는 현재 담당 CTO 권한 아래 지정된 과거 보드의 개발·QA Task,
  최신 보고서와 실행 참조, 제출·인수 기록과 실제 조회된 생산자 Run, 독립 QA 저자의 정상
  종료, Core 영수증 및 현재 승인된 Commit/Tree를 대조한다. 최신 실패를 건너뛰어 옛 PASS를
  고르지 않는다. 생산자 실패·취소가 보존된 경우는 수신한 Commit의 출처일 뿐 성공이 아니다.
  물리 `c69915a`의 관련 44개와 타입 검사가 통과했다. Core/Git 응답은 합성이며 reader는
  현재 G6를 만들거나 실행을 시작하지 않는다. 정확한 비교 pair, ACK 뒤 현재 Task와 이
  원본 증거를 새 VERIFIED·Manager에 결속하는 작업은 남아 있다.

### 영향 없는 Task의 QA 증거 승계

- 현재 담당 CTO의 권한 아래 G5 비교 전·후와 ACK 뒤 실제 Task 보드의 개발·QA 입력을
  각각 확인한다. 세 보드의 출처와 digest는 별도로 보존한다. 승인된 입력·QA 계획·현재
  Source의 Commit/Tree가 같고 최신 QA 보고서와 실행 참조가 일치할 때만 승계한다.
  필요한 근거가 없거나 권한이 철회되면 승계하지 않는다.
- 새 VERIFIED에는 현재 Task/QA 핀과 별도 승계 근거를 넣되 옛 보고서·Core 영수증은
  다시 작성하지 않는다. Manager는 CTO 권한을 재사용하지 않고, 권위 있는 VERIFIED와
  현재 Task·보고서를 검증한다. 실제 Git 효과 요청에는 해당 발행 head·소스/권한 가드와
  정확한 수신 Commit/Tree의 보고서 참조를 함께 넘긴다. 최종 후보도 이 바인딩을 확인한다.
- 등록 생산자 체인에서 QA 승계와 조회·발행 경합 차단을 독립 검사했다. 초기 전체 회귀의
  4개 실패는 보존했다. 두 번째 Workstream의 합성 스냅샷이 첫 번째 QA Task/실행 참조를
  담던 문제를 고쳐 자기 근거를 사용하도록 했고, 다른 Source의 보고서는 계속 거부된다.
  고정 SDK `c69915a` 사본의 관련 136개와 타입 검사가 통과했다. 실행 관련 406개 소스와
  후보 SDK `8a389d8`의 98개 파일을 물리 QA 사본과 일치시켜 전체 회귀 1,581개·타입·빌드를
  확인했다. 여기서 Core·Git 응답은 합성이며 실제 모델·OS·설치본 인수 또는 G7·최종 승인
  완료가 아니다. 입력 브랜치 변경을 Git 쓰기와 같은 트랜잭션에서 막는 검증은 남아 있다.

### Manager 세션 실행 대기와 종료 이벤트

- 다른 Workstream의 Manager Run이 실제로 활성 상태면 두 번째 VERIFIED는 기존 인수
  원장의 `requestId: null`, 실행 시도 0회 예약으로 기다린다. 의존 대기·실행 오류와 구분하며
  새 Agent나 큐를 만들지 않는다. 동일 Workspace Worker의 관련 Job 처리만 직렬화한다.
- 현재 Manager의 정상·실패·중단·시간초과 종료 사실이 확인되면 보호 테스트 후속 실행을
  먼저 조정하고, 현재 설계·권한·검증을 다시 읽어 아직 실행하지 않은 다음 요청 하나를
  인수한다. 취소, 변경된 소스 근거, 오래된 종료 이벤트와 중복 이벤트는 새 실행을 만들지 않는다.
  대기 예약을 쓰는 도중 취소되는 경합과 기존 보호 continuation의 우선순위를 검사했다.
- 실행 소스 406개가 일치하는 후보 SDK `8a389d8` 물리 사본의 전체 회귀 1,589개·타입·
  빌드가 통과했다. 고정 SDK `c69915a`에서도 관련 76개·타입 검사를 확인했다. 이벤트·
  Manager Run은 합성 응답이며 실제 두 CTO 모델 병렬 실행이나 제품 전체 인수는 아니다.
- Core 후보 `ea01cf7`은 `interrupted`·`timed_out`을 성공으로 바꾸지 않고, 저장 Run과
  Node 종료 영수증이 일치한 경우만 기존 종료 이벤트를 발행한다. Main 재검사의 임시 PG
  9개가 통과했다. Node·실행 주체는 시험 자료이며 실제 모델·앱 인수는 아니다.
- 이미 요청 ID를 예약했지만 Core 접수 영수증이 없는 경계와 늦은 Node 종료 확인 이후의
  재발행은 별도 선행 의존성이다. `null` 조회나 timeout을 미접수로 추정하지 않으며,
  이 변경을 모든 재시작·다중 Worker 경합의 자동 복구 완료로 해석하지 않는다.
