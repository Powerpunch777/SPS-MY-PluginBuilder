# 명세 Revision 데이터 검증

v15 5장의 개념 예시인 `ApprovedSpecRevision`에 대응하는 Builder 내부 순수 검증기를
`src/domain/specification-revisions.ts`에 추가했다. 기존 SDK의 실제 export나 Core 모델로
취급하지 않는다.

## 확인하는 것

- 지정된 Builder 프로젝트 ID와 일치하는 명세인지.
- 명세 ID, 제품 규모 S/M/L/XL, 요구사항/수용 기준 ID와 설명, 지원 납품 대상,
  데이터 정책과 승인 근거 참조의 형태가 올바른지.
- 중복 요구사항 ID·대상·한 요구사항 안의 중복 수용 기준 참조, 잘못된 열거값,
  알 수 없는 필드와 getter·희소 배열·사용자 정의 prototype을 거부하는지.
- 호출자가 원본을 나중에 바꾸더라도 검증 결과가 변하지 않는지.

한 명세에는 요구사항과 납품 대상이 각각 하나 이상 있어야 한다. 저장 경계는 최대
요구사항 1,000개, 각 요구사항의 수용 기준 참조 100개, 설명 8 KiB, 전체 검증된 JSON
192 KiB다. 이는 이 구현의 명시적인 입력 한도이지 Core의 전체 용량 보증이 아니다.
서로 다른 요구사항이 같은 수용 기준을 참조하는 것은 허용한다.

## 확인하지 않는 것

`approvalEvidenceRef`라는 문자열이 있다고 실제 고객 승인이 있었다고 판단하지 않는다.
참조하는 정책·승인·수용 기준 자료가 실제로 존재하는지도 이 검증기만으로 알 수 없다.
라이선스 권리, 외부 서비스 실행, Core 권한, Lead 역할이나 프로젝트 업무 성공도 판정하지
않는다. 이 연결이 없으면 명세를 승인 완료로 표시하거나 Graph 변경 근거로 사용할 수 없다.

저장·UI·AI 도구에는 아직 연결하지 않았다. 사용자 답변을 설계에 반영할 때 중복 승인을
요구하지 않는 v15 원칙을 바꾸거나 새로운 승인 화면을 만든 작업도 아니다.

## 검사

프로젝트 불일치, 정확한 필드, 공유 수용 기준, 깊은 복사·동결, getter 비실행, Unicode
바이트 한도와 잘못된 입력을 검사했다.

SDK source pin `316c56f247813e3ec19037b3a3f079d1caa7b739`를 사용하는 별도 임시 복사본에서

`246da081d5e9680ef7ec8e8c9c1ccc3739e7b22ea2088cf78572ad231ac6636f`다.
빌드 전용 시험이며 실제 앱/AI/설치본/실기기 시험이 아니다. 원래 DEV 의존성은 교체하지 않았다.
