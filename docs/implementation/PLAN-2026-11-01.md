## 경계와 기준

- Builder를 사용하는 프로젝트에서 SPS Core Workspace는 선택 가능한 데이터 경계다. Lead/CTO/Development/QA 역할, 명세·Graph/Revision·질문·인수 판단은 Builder workflow가 소유하며 Core 전체에 강제하지 않는다.
- 최신 보고된 SDK pin은 위 2026-11-02 절에 적었다. `61a929f6c783f78e5af603682de1543c7e24abc0`은 이 문서의 이전 historical snapshot이다. 사설 Core 소스를 이 저장소로 복사하지 않는다.
- Workspace Worker, scoped state, UI Bridge, Host React, SDK 빌드·검증·패키징을 재사용한다. 별도 SaaS/Electron/DB/범용 큐/AI Harness를 만들지 않는다.
- Host는 Plugin을 설치하고 Workspace별 활성화를 선택한다. Builder 활성화·Primary 지정은 선택 사항이며, Core 기본 화면 교체나 Core 메뉴 주입은 하지 않는다.
- Core의 Native Settings/tray/전역 단축키 및 시스템 관리는 plugin UI와 독립한다. public SDK가 제공하는 설정 진입 affordance는 선택 사항이다.
- OS 사용자 경계의 파일 접근 제한과 Vault plaintext 보호는 필수 목표다. Trusted mode의 OS 파일 경계 강제는 현재 부분/미완료이므로 구현 완료로 표시하지 않는다.
- 실제 CLI 인증정보·고객 자료·로컬 경로·초대·운영 로그를 공개 Git에 넣지 않는다. 사용량 제한을 우회하는 계정 순환도 구현하지 않는다.

### 질문 대화 조회 수정

질문 화면은 Builder에 저장된 `decisions` 채널의 Lead 대화(`actorId: null`)를
조회한다. 실행 ID인 `runId`를 질문 ID와 비교하지 않으며 CTO/Worker 기록은

## 현재 저장 계약

`scopeKind=company`, Host에서 전달한 Workspace ID, `namespace=sonpark.my-builder`, `snapshot.v1`을 사용한다. 요청 JSON의 임의 Workspace ID는 액션 범위를 바꿀 수 없다. 상담 입력은 사용자 액션으로만 저장하고, 요청 ID 재사용 시 다른 내용은 거부한다. 전용 Workspace Worker의 단일 작성 경로 안에서 직렬화하며 자체 메모리 큐를 영속 작업 큐나 여러 프로세스 간 원자성이라고 주장하지 않는다.

현재 초기 snapshot은 상담·화면 상태의 기반이다. 장기간 전체 대화/문서를 무한히 하나의 JSON에 쌓는 최종 저장 설계가 아니다. 실제 Core 저장 크기·조회 한계와 Lead/CTO 기록 요구를 조사한 뒤 변경 단위·불변 Revision·메시지 페이지를 분리한다. 이를 위해 별도 DB를 먼저 만들지는 않는다.

초기 구현은 JSON으로 인코딩된 상담 요청을 48 KiB, 저장 snapshot을 192 KiB로 제한한다. 제한을 넘으면 기존 기록을 지우거나 읽을 수 없는 큰 상태를 저장하지 않고 실패한다. Native UI의 유한한 요청·응답 크기 안에서 읽기를 보장하기 위한 임시 기술 한계이며, 실제 AI 대화 구현 전 메시지/Revision의 페이지 저장으로 전환한다.

## 검증과 작업 분담

총괄은 경계·저장·실행·통합과 최종 검수를 맡고 Luna high는 독립적인 도메인 검증·표현 UI·확정 규약의 테스트를 맡는다. 각자 파일을 나눠 같은 Core/SDK/lockfile을 동시 수정하지 않는다. 한도가 끝나면 같은 담당자에게 이어서 진행하도록 요청하며 모델/계정 우회로 성공을 가장하지 않는다.

초기 검사는 타입 검사, 실제 SDK validate/Worker lifecycle, Workspace별 저장·실패·중복 요청 검사, Chrome desktop/mobile 실제 조작으로 구성한다. Core 설치본·실제 Google/Codex·Runner·운영 상태와는 구분한다. 실패한 로컬 브라우저 시도는 성공 증거가 아니며, 수정 후 같은 시나리오를 다시 수행해야 한다.

### 실제 Host 연결 후속 검증

`scripts/test-core-host.mjs`가 비공개 Source의 명시적 source-only 외부 시험 도구를
호출하고 `scripts/core-host-acceptance.mjs`가 Builder 고유 검사를 수행한다. Core에는
Builder 제품 이름·업무 모델·역할·설치 자동화를 추가하지 않았다. 시험용 패키지는
새 임시 폴더에 복사하며 `node_modules`, Core 소스, 실제 인증정보는 포함하지 않는다.

실제 앱 시험에서 세 문제를 찾아 수정했다.

1. `companyActivation.defaultEnabled` 누락으로 설치만 해도 활성화되는 문제:
   `false`를 명시했다. 회귀 테스트는 수정 전 실제 실패했다.
2. 그래프 하위 CommonJS 의존성의 `require("react")`로 Host에서 UI가 빈 화면인 문제:
   esbuild resolver adapter로 동일한 외부 Host React를 사용한다. 브라우저 전역
   `require`, Node 통합, 두 번째 React 사본은 추가하지 않는다.
3. Core가 주입한 신뢰 Workspace 메타데이터를 상담 입력의 미지 필드로 거부하는 문제:
   context와 일치하는 메타데이터만 분리하고 실제 입력 검증은 유지한다. 외부 Workspace
   메타데이터는 Worker 회귀 검사에서 저장 요청 전에 거부한다.

수정 뒤 실제 UI Bridge 저장, Workspace A/B 분리, 중복 요청의 단회 저장,
명시적 Shell 선택, Host 재시작 및 활성화 껐다 켜기 후 기록 보존이 통과했다.
네 Main 프로세스가 모두 정상 종료했고 여덟 출력 스트림과 임시 데이터 정리도 완료했다.
독립 Preview 성공을 Host 성공으로 대체하지 않았으며, 앞선 실패는 성공 기록이 아니다.

최근 기록은 필요할 때 여는 drawer로 표시하도록 후속 보완했다.

현재 `npm run check`는19/19 및 SDK validate/test, 전체 의존성 감사는0건이다.
독립 브라우저 검사도 desktop/mobile과900px 임베드 조건을 통과했다. 원격 CI는

## 참고 구현

### 선택 TXT 입력 후속

기존 상담 입력 UI에 로컬 UTF-8 `.txt` 파일 선택과 편집 미리보기를 연결했다.
파일 선택은 저장이나 AI 실행이 아니다. 기존 명시적 저장 액션과 Workspace
저장 계약을 그대로 사용하며, 원본 파일명·로컬 경로를 영속 메타데이터로 추가하지
않는다. 현재 기능은 일반 텍스트 가져오기에 한정되고 상담 출처·발신자·첨부
정규화나 전체 v15 Import 완료를 뜻하지 않는다.

파일 읽기 전 48 KiB 한도를 검사하고, 엄격한 UTF-8/선두 BOM 하나 및 실제
JSON 요청 크기를 검사한다. UTF-16·잘못된 UTF-8·제어문자·빈 파일·중복 BOM은
기존 입력을 보존한 채 거부한다. 늦게 끝난 읽기는 후속 편집·다른 파일·창 닫기를
덮어쓸 수 없다. 읽는 중 저장을 막고, 저장 중 입력 변경을 막는다.

`npm run check`33/33과 SDK validate/test, 독립 Chromium desktop/mobile 검사를
통과했다. 지연 읽기 검사는 읽기를 명시적으로 완료한 뒤 렌더 프레임을 기다리며
임의 시간 경과를 완료 증거로 쓰지 않는다. 전체 `npm audit --audit-level=high`는
당시 취약점0건이었다. 최종 실제 Host 재검사와 원격 CI는 별도 결과로 기록한다.

후속 최종 UI 번들(`9d321a3eda40e85c9bd438377cb219db8318857d429bf87bd2504444671042a9`)
기준 `SPS_BUILDER_CORE_DESKTOP`을 지정한 `npm run test:core-host`도 통과했다.
실제 source Electron/SPS Host에서 잘못된 UTF-8 파일은 편집 입력을 보존하고,
정상 파일 선택은 미리보기만 변경하며 실제 DB 메시지는 비어 있음을 확인했다.
명시적 저장 후 실제 UI Bridge/Workspace 저장, 중복 요청, Workspace B 격리,
Lead 지정 및 원래 Agent 설정 불변, Host 재시작·활성화 전환 후 보존을 확인했다.
네 Main이 정상 종료했고 여덟 출력 스트림 및 정확한 임시 데이터 정리가 끝났다.
Source `dc14d076`/Core `431e2e67` 기반에 미커밋 Registry 입력 후속 코드가 있는
개발 작업 트리 검사다. 최종 설치본·실제 AI·전체 자손·두 PC나 전체 v15 완료로
간주하지 않는다. 공개 Git에는 실제 사용자 자료·원시 경로·앱 로그를 넣지 않는다.

공식 [MDN File API](https://developer.mozilla.org/en-US/docs/Web/API/File_API)와
[TextDecoder](https://developer.mozilla.org/en-US/docs/Web/API/TextDecoder)를
참고하고 브라우저의 기존 File API를 재사용했다. 자체 파일 업로드 서버나 파일
감시·크롤러·새 AI 실행기는 만들지 않았다.

### Lead Agent 설정 후속

시스템 화면에서 같은 Workspace의 기존 Agent를 선택해 별도 `lead-agent.v1`
레코드에 저장한다. 기존 상담 snapshot, Agent의 adapter 설정·폴더·세션은 바꾸지
않는다. UI에는 ID·이름·상태만 전달하고 adapterConfig·인증정보·로컬 경로는
전달하지 않는다. 선택 가능한 상태는 현재 `idle/running`이며, 이는 provider 로그인,
실행 권한이나 준비 완료의 증명이 아니다. `integrations.ai`와 전송 버튼은 아직
사용 가능 상태로 바꾸지 않았다.

저장은 사용자 액션과 현재 revision이 일치할 때만 수행한다. 동시 저장 충돌,
다른 Workspace의 Agent, 잘못된 메타데이터·저장 실패를 거부한다. 삭제되거나
조회할 수 없는 기존 선택은 자동으로 다른 Agent로 바꾸지 않고 명시적으로
사용 불가 상태를 표시한다. 설정 안 함으로 해제할 수도 있다. 현재 단일 작성자
직렬화는 프로세스 간 DB 트랜잭션이나 장기 실행 큐가 아니다.

실제 Host 검사에서 Workspace 전용 Worker가 `agents.list`를 처리하지 않아502가
발생했다. SDK 선언을 믿고 성공으로 처리하지 않았고, Core에서 기존 목록 조회
하나만 capability와 정확한 Workspace invocation 아래에 연결했다. 이 수정은
Core `21f2feb21e75d0ef40db3aa4de4609968da7ea33`에 있다. 세션·호출·Agent 변경
권한을 함께 열지 않았으며, UI는 지원하지 않는 Host에서는 목록 오류를 표시한다.
이 historical 검증 당시 SDK `61a929f...`의 세션 API는 일반 Host 경로에 존재하지만 Workspace 전용 경로의
지원과 최종 답변 계약은 다음 단계에서 별도로 확인해야 한다. Legacy Host Worker로
우회하거나 별도 AI 서버/Runner를 만드는 방식은 사용하지 않는다.
