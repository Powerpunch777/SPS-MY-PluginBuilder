# Builder 병행 구현 계획

2026-11-01. 사용자 지시로 Core 안정화와 별도 레포에서 병행 개발을 시작했다.
원본 v15 설계와 UI v9는 변경하지 않는다. 제품 완성이나 Core 통합 완료 선언이 아니다.

## 경계와 기준

- 고객 프로젝트의 기본 데이터 경계는 SPS Core Workspace다. Lead/CTO/Development/QA 역할, 명세·Graph·Revision·질문·인수 판단은 Builder가 소유한다.
- SDK는 공개 commit `61a929f6c783f78e5af603682de1543c7e24abc0`으로 고정했다. 사설 Core 소스를 이 저장소로 복사하지 않는다.
- Workspace Worker, scoped state, UI Bridge, Host React, SDK 빌드·검증·패키징을 재사용한다. 별도 SaaS/Electron/DB/범용 큐/AI Harness를 만들지 않는다.
- Host는 Builder를 설치하고 Workspace에서 활성화·Shell을 선택한다. 자동 설치·Core 기본 화면 교체는 하지 않는다.
- 실제 CLI 인증정보·고객 자료·로컬 경로·초대·운영 로그를 공개 Git에 넣지 않는다. 사용량 제한을 우회하는 계정 순환도 구현하지 않는다.

## 진행 순서

| 단계 | 범위 | 현재 |
| --- | --- | --- |
| 1. 독립 기반 | 타입·검증·Workspace 범위·SDK Worker·상담 텍스트 단회 저장 | 초기 구현 및 로컬 13개 검사 통과 |
| 2. UI | v9 탐색·Lead 채팅·하위 세션 조회·문서·Graph·질문·시스템·반응형 | 초기 빈 상태/선택 텍스트 화면의 desktop/mobile 조작 통과; 실제 세션·Graph 편집 미구현 |
| 3. 실제 Host | 두 Workspace 활성화, 실제 bridge/state, 중지·재시작 후 기록, Shell 선택 | 미검증 |
| 4. AI 연결 | 기존 Core Agent 세션/실행·취소 기능 조사 후 주 실행 경로 하나 선정; Lead 3세션/CTO 단일/Worker 독립·상위 기억 경계 | 미구현 |
| 5. 설계·업무 | Lead의 명세/Graph Patch, CTO 업무 배정, 미결정 답변 Revision 반영, QA 증거 연결 | 미구현 |
| 6. 납품 | GitHub PR/Actions/Runner 조회·검증·Artifact·고객 인수 및 Release | 미구현 |

UI가 나타나거나 SDK 테스트가 통과한 것을 실제 AI 개발·Host 통합·납품 검증으로 표시하지 않는다. 기존 Core 실행 기능이 충분한지 확인한 뒤만 앱서버/SDK 추가 필요성을 판단한다. AI 코드가 아직 없으므로 메시지 전송은 비활성이다.

## 현재 저장 계약

`scopeKind=company`, Host에서 전달한 Workspace ID, `namespace=sonpark.my-builder`, `snapshot.v1`을 사용한다. 요청 JSON의 임의 Workspace ID는 액션 범위를 바꿀 수 없다. 상담 입력은 사용자 액션으로만 저장하고, 요청 ID 재사용 시 다른 내용은 거부한다. 전용 Workspace Worker의 단일 작성 경로 안에서 직렬화하며 자체 메모리 큐를 영속 작업 큐나 여러 프로세스 간 원자성이라고 주장하지 않는다.

현재 초기 snapshot은 상담·화면 상태의 기반이다. 장기간 전체 대화/문서를 무한히 하나의 JSON에 쌓는 최종 저장 설계가 아니다. 실제 Core 저장 크기·조회 한계와 Lead/CTO 기록 요구를 조사한 뒤 변경 단위·불변 Revision·메시지 페이지를 분리한다. 이를 위해 별도 DB를 먼저 만들지는 않는다.

## 검증과 작업 분담

총괄은 경계·저장·실행·통합과 최종 검수를 맡고 Luna high는 독립적인 도메인 검증·표현 UI·확정 규약의 테스트를 맡는다. 각자 파일을 나눠 같은 Core/SDK/lockfile을 동시 수정하지 않는다. 한도가 끝나면 같은 담당자에게 이어서 진행하도록 요청하며 모델/계정 우회로 성공을 가장하지 않는다.

초기 검사는 타입 검사, 실제 SDK validate/Worker lifecycle, Workspace별 저장·실패·중복 요청 검사, Chrome desktop/mobile 실제 조작으로 구성한다. Core 설치본·실제 Google/Codex·Runner·운영 상태와는 구분한다. 실패한 로컬 브라우저 시도는 성공 증거가 아니며, 수정 후 같은 시나리오를 다시 수행해야 한다.

### 2026-11-01 초기 검증

- `npm run check`: 타입 검사, 소스 재빌드, 13/13 테스트, SDK 정적 검증 및 Worker 생명주기 통과. 테스트 전에 매번 빌드하므로 기존 `dist`가 있어야만 통과하는 순서 의존을 제거했다.
- Worker 검사는 빌드된 실제 `dist/worker.js`를 별도 프로세스로 실행해 SDK JSONL과 제한된 가짜 Host state를 왕복했다. 두 Workspace의 분리와 범위 변경 요청 거부를 확인했다. 실제 SPS 서버 검사는 아니다.
- `npm run test:browser`: 실행 중인 loopback Preview에서 Chrome 1440x900 및 390x844, 여섯 메뉴, 선택 텍스트 입력, 사이드바/모바일 기록 패널, 입력창 표시 및 가로 넘침을 확인했다. Preview 입력은 메모리에만 남는다.
- `npm audit --audit-level=high`: 개발 의존성을 포함한 당시 감사에서 취약점 0건. 향후 감사 결과가 같다고 보장하지 않는다.
- 배포 검사로 소스·설계 문서·개발 도구·`node_modules`는 배포 allowlist에서 제외되고, SDK 및 실제 번들 UI의 LICENSE/NOTICE는 포함됨을 확인했다.
- 새 GitHub CI는 Node 22.18.0/24의 깨끗한 checkout에서 `npm ci --ignore-scripts`, 프로덕션/전체 감사, `npm run check`를 실행한다. 원격 결과는 실제 실행 후 별도로 기록한다. 브라우저 검사는 아직 로컬 전용이다.

다음 구현은 실제 격리 Host의 UI Bridge·Workspace state·Shell 선택·재시작 보존 검증이다. 그 다음 기존 Core Agent 실행 경로를 연결하며 별도 AI 실행 서버를 만들지 않는다. 주 Lead 세 세션, 실제 Worker 실행, Graph Patch·미결정 답변·납품 연결은 아직 구현 완료가 아니다.
